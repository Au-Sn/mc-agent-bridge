# 历史问题统计与规避纪律（Lessons Learned）

> 来源：本项目在 **原版（mineflayer / MCP）** 环境下的一次完整实战会话——从空手起家到建成小屋、完成铁甲、分类箱子。
> 目的：把踩过的坑固化成**可执行的规则与检查表**，不再重犯。

---

## 0. 统计总览

| 分类 | 条数 | 最严重的后果 |
|---|---|---|
| A 生存与环境 | 5 | **死亡 3 次**，累计掉落整套铁甲 + 工具 + 材料 |
| B 工具/接口语义 | 22 | 反复返工、隐形空洞、白挖、搬运无效；**写入 BOM → 存档崩**；**跨语言习惯 → 首次运行崩**；**凭记忆给命令/API → 不可用**；**拿噪点遥测推断物理机制 → 结论完全错**；**无 id 握手的协议 → 结果错位** |
| C 建造与施工 | 10 | 4 处结构性缺陷（3 处由用户发现） |
| D 状态与协作 | 4 | 认知与现实脱节、抢救过期 |
| E 连接与模组环境 | 8 | 无法进入 Forge 服务器；**装模组后游戏启动崩溃**；**启动永久卡死**；**窗口被扔到屏幕外打不开**；**中文回传乱码** |
| **合计** | **49** | — |

**三条最值钱的结论**（详见后文规则）：

1. **工具回报的数不可信** → 一切"完成"必须用**独立计数**核对
2. **改地面/改墙体前，先想"谁靠它撑着"** → 门、台阶、火把的脱落都源于此
3. **夜晚 + 开阔地 + 远行 = 死亡** → 夜间不进掩体就会反复出事

## A. 生存与环境

### A1｜挖阶梯挖通地下水脉，淹死（致命）
- **现象**：向下挖 `dig_staircase` 时穿透含水层，氧气迅速归零，血量 20 → 2.2，随后死亡
- **根因**：下挖前**没有探测水体**；身上无护甲；氧气归零后没有立即上浮
- **损失**：14 粗铁、钻石剑、煤炭、石镐
- **规避规则**
  - 下挖前先 `get_block_at` 逐格探测 **y-1 / y-2 / y-3**，遇 `water` 立刻换点
  - 下挖必须**穿全套护甲**
  - `oxygen < 10` 立即上浮（`jump` 控制），不要恋战
  - 已知含水层的坐标要记入笔记，永不二次开挖

### A2｜夜间在开阔地被苦力怕炸死 ×2（致命）
- **现象**：夜间在基地空地待机，两次死亡间隔仅 30 秒，**满血瞬间归零**（苦力怕贴脸）
- **根因**：夜间露天站桩；基地周边**无照明**；没有封闭掩体
- **损失**：整包（含刚烧好的 24 个铁锭与全套铁甲）
- **规避规则**
  - **夜间（timeOfDay > 13000）必须进封闭掩体**，或先完成周边照明
  - 基地/住所周边**四向都要有火把**（缺一面就是固定刷怪点）
  - 夜间禁止在露天长距离移动

### A3｜幻翼（Phantom）持续袭击
- **现象**：连续多日在游戏内不睡觉，幻翼每夜刷新并反复俯冲，血量被磨、护甲耐久持续下降
- **根因**：久未睡眠（游戏机制）
- **规避规则**：**做床睡觉**是唯一根治手段；床需要 **3 张同色羊毛**（羊多为白色，优先凑 3 白）

### A4｜追猎物拖到入夜，困在远处海岸死亡 ×2（致命）
- **现象**：为凑羊毛跑到 50+ 格外，夜幕降临仍在开阔地，30 秒内连死两次
- **根因**：**收益低、风险高的远征没有时间预算**；出发时白天，结束时已入夜
- **规避规则**
  - 远征前先看 `timeOfDay`，**预留返程时间**（日落 = 13000）
  - 天黑前 1000 tick 必须开始返程
  - 低价值目标（羊毛/肉）不值得冒夜间风险

### A5｜掉进自己挖的深井，寻路出不来
- **现象**：`goto` 返回 `NO_PATH`，机器人在竖井底部无法脱离
- **根因**：1×1 竖井需要"垫脚"能力，默认寻路不含
- **规避规则**
  - 先 `configure_movements(allow1by1towers=true, scaffoldingBlocks=["cobblestone","dirt"])`
  - 仍失败则**分小步 `goto`**（每次向上 2–3 格），比一次性大目标可靠
  - 挖竖井时**顺手挖成阶梯**，不留垂直陷阱

## B. 工具 / 接口语义（最容易吃亏的一类）

### B1｜`dig` 挖下的掉落物不会自动进包
- **现象**：明明挖掉了方块，背包数量不增加
- **根因**：掉落物生成在方块中心，**超出拾取半径**；`dig` 不做拾取
- **规避规则**：**挖完必须走过去**（`goto` 到方块坐标）或用 `collect_block`；
  每次挖掘段落结束后**核对背包数量**

### B2｜`place_block` 的 `itemName` 不会真正换手
- **现象**：想放门，结果门洞里出现**沙子 / 泥土 / 楼梯**
- **根因**：该参数不保证切换手持物，实际使用的是当前手持物
- **规避规则**
  - 放关键方块前：`equip_item` 或 `set_quickbar_slot` → **`get_state` 确认 `heldItem`** → 再 `place_block`（不要传 itemName）
  - 若装备无效：**把物品丢到地上再捡起**（拾取优先进入快捷栏空位），再切槽

### B3｜物品不在快捷栏就无法装备
- **现象**：`equip_item(oak_door)` 返回成功但手持物没变
- **根因**：装备接口只对**快捷栏槽位（36–44）**内的物品可靠
- **规避规则**：需要使用的方块/工具**先弄进快捷栏**（见 B2 的"丢-捡"法）

### B4｜`move_slot_item` / `transfer_items` 空操作
- **现象**：返回 `ok` 但槽位内容不变；`transfer_items` 直接内部报错
- **规避规则**：不要依赖槽位搬运接口做关键整理；改用**箱子存取**（`container_*` + `click_window`）

### B5｜自动进食（autoeat）干扰一切放置/装备
- **现象**：手持物在放置瞬间被换成食物；装备后立刻被改回
- **根因**：`minHealth=20` 意味着"只要没满血就吃"，受伤时机器人不停切换手持物进食
- **规避规则**
  - **精确建造/放置前临时关闭 autoeat**，做完再开
  - 阈值改合理值（如 `minHealth=12~16`、`minHunger=14`），别设成"永远饿"

### B6｜`fill_region` 会静默跳过格子，回报数不可信
- **现象**：报告 `placed: 18 / skipped: 16`，但墙体仍出现**看不见的空洞**（北墙 2 格、屋顶 2 格）
- **根因**：填充要求格子有**相邻实心面**；同批次里后放的格子在当时还没有支撑 → 被跳过
- **规避规则**
  - **分层填，先下后上**（下层填完再填上层）
  - **填完必须用 `get_blocks_in_region` 计数核对**（预期数 vs 实际数），差一个都要补
  - 内部填充需要二次补填（第一次落边缘，第二次落内部）

### B7｜`container_deposit` 不带 count 只搬 1 个
- **现象**：分类时每样只搬走 1 个，箱子里剩一堆
- **规避规则**：**整叠搬运一律用 `click_window(slot, 0, mode=1)`**（shift 点击）

### B8｜`click_window` 的 mode 语义
- **规避规则**：`mode=1` = shift 点击 = **整叠转移**；容器槽 0–26、玩家背包 27+；
  槽号必须**当场 `read_open_container` 现读**，不要用上一轮的缓存

### B9｜`smelt_item` 容易超时
- **现象**：请求 24 个，只出了 2 个就 `TIMEOUT`
- **规避规则**：改手动流程——`open_furnace` → `furnace_action(put)` →
  `wait_for_ticks` 轮询 → `furnace_action(take)`；**分批投料，每批核对产出**

### B10｜`place_block` 因身体占用目标格被拒
- **现象**：报 `the block is still air` 或超时，但目标其实合法
- **根因**：机器人实体占住了目标格
- **规避规则**：**先退开 1–2 格**再放置；放置后立即 `get_block_at` 确认

### B11｜相邻箱子会合并成大箱子
- **规避规则**：分类箱之间**留 1 格间隔**

### B12｜`get_blocks_in_region` 参数必须是对象
- **现象**：`expected object, received array/string`；以及反复出现的 JSON 多余大括号
- **规避规则**：固定模板
  ```json
  {"min":{"x":..,"y":..,"z":..},"max":{"x":..,"y":..,"z":..},"matching":["..."],"maxCount":N}
  ```
  写完先自查括号数量，不要拼接字符串

### B13｜**写配置文件写出 BOM** → 存档一加载就崩（真实事故，代价最高的一条）
- **现象**：世界加载到一半，服务端直接崩，日志只给一句看起来莫名其妙的错：
  ```
  ConfigLoadingException: Failed loading config file computercraft-server.toml of type SERVER
  Caused by: ParsingException: Invalid bare key: ﻿#The
                                                      ↑ 这个看不见的字符就是元凶
  ```
  `#The` 前那个字符是 **UTF-8 BOM（字节 `EF BB BF`）**
- **根因**：我用 PowerShell 写配置文件时用了 `Set-Content -Encoding UTF8`。
  **Windows PowerShell 5.1 的 `-Encoding UTF8` 会强制写入 BOM**。
  > 事后确认：本机 harness 的 `$PSVersionTable.PSVersion` = **5.1.26100.1591**，
  > 即确实是 5.1 语义（`-Encoding UTF8` 带 BOM；`utf8NoBOM` 这个参数名在 5.1 里根本不存在）。
  > 在 5.1 下要写无 BOM 文件，只能用 .NET 的 `UTF8Encoding($false)` 或 `-Encoding ASCII`。
  TOML 解析器（nightconfig）不会跳过 BOM → 开头的 `#` 不再被识别为注释 →
  解析器把 `#The ...` 当成**键名** → 整份 `computercraft-server.toml` 解析失败 → **服务端启动崩溃**
- **放大效应（最要命的一点）**：Forge 的 `defaultconfigs/` 会被**复制成新世界的 serverconfig**，
  所以一个带 BOM 的 `defaultconfigs\computercraft-server.toml` 会**污染之后创建的每一个世界**
  （本次 `新的世界` 与 `新的世界 (1)` 双双中招，两个存档都进不去）
- **规避规则**
  - **禁止**用 `Set-Content` / `Out-File -Encoding UTF8` 写游戏配置文件
    （PS 5.1 的 `UTF8` 带 BOM；PS 7 要用 `utf8NoBOM`）
  - 需要脚本写文件时，用**明确无 BOM**的写法：
    `[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`
  - **写完必须回读字节头复核**：正常开头是 `23`(`#`) 或 `5B`(`[`)；
    看到 **`EF BB BF` 就是 BOM，必须去掉**（去掉时只删前 3 字节，其余内容原样保留）
  - 改完配置**先启动一次**再进世界（这类错误会停在启动/加载阶段，**不会写坏存档**，是可恢复的）
  - 纯文本改动用编辑器另存为「UTF-8 无 BOM」比用脚本更安全
  - 复查命令（一次扫清所有隐患）：
    ```powershell
    Get-ChildItem <实例>\config,<实例>\defaultconfigs,<实例>\saves -Recurse -File -Filter *.toml | ForEach-Object {
      $fs=[System.IO.File]::OpenRead($_.FullName); $b=New-Object byte[] 3; $null=$fs.Read($b,0,3); $fs.Close()
      if ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { $_.FullName } }
    ```

### B14｜跨语言习惯写进 Lua → 游戏内第一次运行就崩（真实事故）
- **现象**：计算机里 `http.get` 明明打印 `Success`（脚本下载成功、放行规则正常），紧接着：
  ```
  [string "agent_bridge..."]:514: attempt to perform arithmetic on a string value
  ```
  用户侧观感是"计算机里的代码没生效"
- **根因**：第 514 行写的是 `print("=" * 52)`。
  **Lua 没有「字符串 × 数字」的重复语法**（那是 Python / PowerShell 的习惯），
  `*` 只能作用于数字 → 对字符串做算术 → 运行期直接抛错并退出
- **为什么本地没拦住**
  - 本机**没有 lua/luac 可执行文件**，无法执行验证；
  - 当时的 `lua_lint.py` 只做**词法**检查（括号/字符串/注释是否平衡），
    `"x" * 52` 词法完全合法，**只有运行到那一行才会炸** → 只能到游戏里才暴露
- **规避规则**
  - Lua 里重复字符串用 **`string.rep("=", 52)`**
  - 写完 Lua **必须过 `py tools/lua_lint.py <file>`**：现已加入"跨语言习惯"规则，
    `"x" * n` / `!=` / `&&` `||` / `None` `True` `False` / `+=` `++` / 行首 `#`
    一律判 **ERROR**；Python/JS 方法名判 WARN
  - **加了规则必须自测**：拿一个故意写坏的小文件跑一遍，确认真的会报错并返回非 0
    （否则"规则存在"只是心理安慰——本次已自测：4 处全报，退出码 1）
  - 认命原则：**没有解释器的语言，只有"在目标环境跑过一次"才算验证过**。
    所以首次上线一律 `dry_run=true`，且 **dry_run 必须放行只读指令**
    （status/scan/players/block_info/chat_read/say），否则连冒烟测试都做不了，等于没验证
  - 现场调试友好性：主循环每轮包一层 `pcall`，
    **一次异常只影响一轮，不要让脚本整体退出**（否则用户得反复重新敲命令）

### B15｜凭记忆写给用户的命令语法是错的（真实事故）
- **现象**：我在聊天里让用户执行 `run http://127.0.0.1:8765/files/agent_bridge.lua`，
  CC 直接回 **`No such program: run`**（用户理解为"没有这个程序"）
- **根因**：**CC:Tweaked 的 ROM 里根本没有 `run` 这个程序**。
  我在聊天里凭记忆写命令，而 `install.md` 里原本写的是**正确的** `wget run <url>`
  —— 说明"随手的记忆"比"已经核对过的文档"不可靠，**改写文档里的正确写法 = 主动引入错误**
- **权威依据**（读 CC:Tweaked 1.115.1 的 jar 得到）：
  - `data/computercraft/lua/rom/programs/` 下没有 `run.lua`
  - `http/wget.lua` 的 `printUsage()` 明确写着：`wget <url> [filename]` 与 `wget run <url>`
- **规避规则**
  - 给用户的**任何命令 / 语法 / ID / 版本**，先回权威来源核对，核对完再写：
    | 要查什么 | 去哪查（都在 jar 里） |
    |---|---|
    | CC 程序与用法 | `data/computercraft/lua/rom/programs/**`（各程序的 `printUsage()`） |
    | 模组物品/方块注册名 | `assets/<modid>/lang/en_us.json` |
    | 模组版本与依赖区间 | `META-INF/mods.toml` |
  - **文档里已有的正确写法，聊天时不要"顺手改写"**
  - 报错原文就是最好的线索：`No such program: X` → 是**命令名**问题，
    不要去查网络/权限/配置（本次差点往 http 放行方向排查，那是完全错的方向）

### B16｜PowerShell 的 `Set-Location` 不改变 .NET 工作目录（**同一个坑踩了两次**）
- **现象**
  - 第一次：脚本里 `Set-Location <项目目录>` 后调 `Bitmap.Save("logs\x.png")` →
    报 **"A generic error occurred in GDI+"**（实际是目录不存在）
  - 第二次：`Set-Location <项目目录>` 后调 `[System.IO.File]::ReadAllBytes("bridge\processed\x.json")`
    → 报 **"Could not find a part of the path ...\deepseek harness\bridge\..."**（少了项目目录一层）
- **根因**：PowerShell 的当前位置（`Get-Location`）与 **.NET 进程的当前目录
  （`[Environment]::CurrentDirectory`）是两个东西**。`Set-Location` 只改前者，
  而 .NET 的文件 API 用的是后者 → 相对路径解析到了完全不同的目录
- **规避规则**
  - **凡是用 .NET 文件/图形 API（`[System.IO.File]`、`Bitmap.Save`、`ZipFile` 等），一律传绝对路径**
  - 需要相对路径时先自己拼绝对：`Join-Path (Get-Location).Path $rel` 再交给 .NET
  - PowerShell 自身的 cmdlet（`Get-Content` / `Test-Path`）跟随 PS 当前位置，
    所以"同一段脚本里 cmdlet 好使、.NET 不好使"这种诡异现象，根因就是这里
  - **同类错误第二次出现时必须升级为规则**（元规则 3）：第一次没写下来，第二次又浪费了一轮

### B17｜外设 API 名不能凭印象：`peripheral.getMethods()` 就是权威来源（真实事故 ×2）
- **现象**
  - `chat_read` 报"无可用的 API：getMessages/readMessages" → 实测该版本 **Chat Box 根本没有读取类 API**
  - `inv_man` 报"无可用的 API：list/getItems" → 真实方法名是
    **`listChest`/`getItemsChest`（读相邻容器）** 与 `list`/`getItems`（读绑定玩家）之分，我漏了 `Chest` 系列
- **根因**：我按"印象中的 API"写候选名。模组版本之间 API 会增删改名，
  **印象 = 猜测**，而猜测在游戏里只会在运行期以"某个功能不可用"的形式暴露
- **处置（本项目已内置的能力）**：程序里加了 **`peripheral_api` 指令**，
  内部用 `peripheral.getMethods(名字)` 把每个外设的**真实方法名**列出来。
  一条指令就把 5 个外设的方法名全部问清（结果同时写进了 `cc-tweaked/install.md` 3.1 节）
- **顺带问出来的关键事实**（凭印象全都想不到）
  - Geo Scanner 有 `cost` / `getFuelLevel` / `getOperationCooldown` → **扫描有冷却**，
    这才是"`scan` 时好时坏"的真正原因（不是网络、不是权限）
  - Player Detector 有 **`getPlayerPos`** → 能拿到**玩家绝对坐标**，
    等于给"自己不知道自己在哪"的 CC 计算机装上了世界坐标锚点
  - Inventory Manager 的 `getItems()` 会报"没有记忆卡或未绑定玩家" → 报错要**分路径报**，
    否则会拿"没记忆卡"去误导一个"只是没贴容器"的现场（已改成两条路分别报原因）
- **规避规则**
  - **不要凭印象写 API 名**。先问环境：CC 用 `peripheral.getMethods()`，
    通常对应的就是一条自省指令；其它平台同理（`--help`、introspection API、`?` 端点）
  - 排查"功能不可用"时，**先分清"方法不存在"和"方法存在但调用失败"**——
    前者要换名，后者要查前置条件（缺容器/缺燃料/在冷却）。
    `callFirst` 已改为记录**最后一个真实错误**，不再统一报"无可用的 API"
  - 一次自省的结果要**写进文档**，否则下一个人（或下一个我）还会再猜一遍

### B18｜CC 的 `wget` **拒绝覆盖已存在的文件** —— 而我又一次凭印象给了指令
- **现象**：我让用户执行 `wget http://.../bridge-live.cfg bridge.cfg` 来"覆盖配置"，
  结果配置文件时间戳纹丝不动、`dry_run` 始终是 `true`（从存档里
  `computercraft/computer/0/bridge.cfg` 的 mtime 直接看出来）
- **根因**（读 CC 的 ROM 源码 `rom/programs/http/wget.lua` 得到）：
  ```lua
  local sPath = shell.resolve(sFile)
  if fs.exists(sPath) then
      print("File already exists")   -- 直接返回，不做任何事
      return
  end
  ```
  **它根本不会覆盖**。我给的"覆盖式下载"从设计上就不可能生效。
- **顺带核实到的好东西**：`run` 分支是 `pcall(func, table.unpack(tArgs))`
  —— **`wget run <url>` 后面的额外参数会传进程序**。
  于是把模式切换做成"一个词"：
  `wget run .../agent_bridge.lua live` / `... dry`，彻底不用碰配置文件
- **规避规则**
  - **给用户的每条命令，先确认它的语义**（会不会覆盖？已有文件会怎样？参数怎么传？），
    而"查语义"的权威来源就是**程序源码**（CC 的 ROM 全在 jar 里，可直接读）
  - **让用户做的操作越少越好**：一次"改配置文件 + 删文件 + 重启"能塌成"重启时加一个词"，
    就一定要塌——用户每多一步，失败概率和往返次数都翻倍（本次为此浪费了两轮）
  - 诊断"改了没生效"这类问题时，**去找那个"证据文件"的时间戳**（本次是存档里的 cfg），
    不要问用户"你到底改了没有"

### B19｜Lua 的 `...` 有作用域：函数里取到的是**函数自己的**可变参数
- **现象**：为支持 `wget run <url> live`，我在 `main()` 里写了 `local mode = ...` ——
  它会**永远得到 nil**（`main()` 被无参调用，函数内的 `...` 是它自己的可变参数）
- **正确做法**：程序启动参数只存在于**主 chunk 的 `...`**，必须在顶层先捕获：
  ```lua
  local ARGV = { ... }      -- 主 chunk 顶层
  local function main() ... local mode = ARGV[1] ... end
  ```
- **规避规则**
  - 换语言时，**"作用域/参数传递"这类语义必须逐条确认**，不能靠"感觉一样"
    （同类前科：`"x" * 5` 见 B14）
  - 这类错误**词法 lint 抓不到**，只能靠"知道这条语义"或"在目标环境实跑"。
    所以：写不熟悉的语言时，**宁可多写两行显式代码，也不要用"看起来像别的语言"的简写**

### B20｜拿噪点遥测去推断物理机制 → 结论完全错（真实事故，**方法论级**）
- **现象**：海龟 `forward n=1`（不挖）后，GPS 的 y 从 72.25 变成 70.04（**掉了 2 格**），
  而燃料只扣了 **1**（= 一次移动）。于是我推断："坠落不耗燃料，所以它是**掉下去**了"，
  并据此在代码里加了"水平移动前必须检测下方有方块"的**默认防坠落拦截**
- **真相（做了决定性实验才发现）**：让海龟 `up n=2`（不挖）→ y 从 70.04 升到 72.45
  （Δ+2.41，耗 **2** 燃料 = 两次移动，精确对上），**8 秒后再读仍是 72.45——没有掉回来**。
  源码里也找不到任何重力逻辑（`TurtleBlock` / `TurtleBlockEntity` 无 fall/onLand/checkSupport）
  → **海龟不受重力、可以悬空**；那个"掉 2 格"其实是 **GPS 的坏解**
- **根因**：CC 的 GPS 用调制解调器**信号强度**估算距离，本身带噪声。
  本次实测同一位置既读到过误差 0.05 格的好解（y=72.45，真值 72），也出现过偏 2 格的坏解。
  我把"噪声"当成了"物理事实"，还**把错误结论固化进了默认行为**——
  这个默认拦截会把浮空岛上最常用的"悬空向外建造"全部挡掉 ✗
- **规避规则**
  - **用遥测数据推断物理机制之前，先验证遥测本身的精度**：
    同一状态**重复采样**几次，看读数是否稳定；不稳定就先解决测量问题
  - **优先做"能直接区分两种假设"的实验**，而不是靠推理链：
    本次 `up n=2 + 等 8 秒再读` 一步就把"有重力/无重力"彻底分开
    （有重力必然会掉回来；实测没掉 → 无重力）
  - **不要把单一观测直接固化成默认行为**：先做成可选开关，等多来源证据一致再改默认值
    （本次已把默认拦截改为按需 `require_ground=1`）
  - **关键决策不能只信一次采样**：定位已改为**多次采样取中位数**
    （`locateMedian`：导航 3 次，状态回报 2 次）
  - 附带收益：查这个问题时确认了"海龟是方块（`TurtleBlock`+`TurtleBlockEntity`）而非实体"，
    且**地质扫描仪能看到它**（`computercraft:turtle_advanced` 出现在扫描结果里）

### B21｜"重启后状态丢失"类 bug：内存里的朝向 → 导航整体走反（真实事故）
- **现象**：让海龟 `goto` 到它**东边**的方块，它却一路往**西**走了 3 格 ✗；
  报错信息还把它自己的目标显示成 `4122,72,7`（我传的是 4121,71,6），看起来像我算错了
- **根因（两个独立问题）**
  1. **朝向只存在内存里**：`facingIdx` 是普通局部变量，用户每次 `Ctrl+T` 重启 worker 就复位成
     "未知/北"，而 `turnToIdx` 仍按旧假设转向 → **方向整体反了**。
     `status` 里其实一直报 `facing: "unknown"` —— **征兆早就摆在眼前，是我没重视** ✗
  2. **显示 bug 误导排查**：错误信息用 `%.0f` 打印"方块中心"（4121.5）→ 四舍五入成 `4122`，
     看起来像我算错了目标 ✗（实际逻辑是对的）
- **修复**
  - **启动时自动测向**：GPS 记位置 → 走一步（不挖；被挡就转 90° 重试，最多 4 个方向）
    → 量位移 → **走回来（净位移 0）** → 由位移反推"前进"对应世界的哪个方向
    → 写入 `facingIdx`。这样**重启后它自己就能重新知道朝向**，不依赖人工校准
  - 展示坐标时用**方块坐标**（`math.floor`），不要格式化"中心值"
  - 报错信息里附带**当前朝向**，让同类问题一眼可见
- **规避规则**
  - **凡是有状态的自动化实体，都要问一句"重启后这些状态还在吗"**：
    朝向、校准值、计数器、当前工序位置……**内存态一律视为会丢**
  - **能自测的状态就别让人输入**：可以靠传感器（本例是 GPS 位移）反推的状态，
    就做成自动测定 + 自愈，而不是"记得每次重启后手工校准"（人一定会忘）
  - **别忽略持续存在的告警字段**：`facing: unknown` 连续出现多次时，它就是根因线索，
    不该当成噪音跳过
  - 报错信息要**能自证**：把"目标是什么、当前朝向、卡在哪"一起报出来，
    否则错误的显示格式会把排查引向完全错误的方向

### B22｜没有 id 握手的"请求-响应"协议 → 超时后结果整体错位（真实事故）
- **现象**：给海龟下指令"时好时坏" —— `equip` / `forward` 报「海龟无响应（10 秒超时）」，
  而 `locate` / `back` 却成功；同一批指令里成功与超时交替出现 ✗
- **两个根因**
  1. **协议没有 id 握手**：主计算机只发 `{cmd=...}`，然后收"**任意一个**" `bridge_reply`。
     一旦某条指令耗时超过等待上限，它**迟到**的回包就会被当成**下一条指令**的结果 ✗✗
     —— 从此整条链路的结果全部错位（这就是"时好时坏"的真相，不是网络抖动）
  2. **启动时做了阻塞操作**：worker 启动时先做"自动测向"（3 次 GPS 采样 + 走一步 + 回来，
     约 15 秒），这段时间它**完全不在监听 rednet** ✗ → 用户一重启就发指令必然超时
- **修复**
  - 每条转发指令带**唯一 id**（`os.epoch("utc") .. "-" .. 序号`），回包原样带回；
    只认 id 相同的回包，其它**丢弃并继续等** ✓
  - 等待上限 10s → **30s**，并支持按指令 `wait_ms` 覆盖（`locate`、`dig_up_while` 这类长活需要）
  - **启动不做阻塞操作**：把"自动测向"挪到**首次真正需要方向时**（`goto`/`tunnel` 内部触发），
    启动即可立刻响应 ✓
  - 测向从"走 1 格"改为"走 **2** 格"：位移 Δ≈2 才压得住 0.7 格的 GPS 噪声
    （走 1 格时 Δ≈1，噪声足以判错轴向 —— 这正是两次自测得出 west / north 不一致的原因）
- **规避规则**
  - **任何"发请求-等响应"的通道，响应必须能对应到具体请求**（id / 序号 / 句柄）。
    只用"等下一个响应"在超时、重试、异步的情况下必然错位
  - **超时值要按"最慢的合法操作"设**，不能按"最快的情况"设（本次 10s 对多采样 GPS 定位太紧）
  - **启动路径上不要放重活**：启动阶段应尽快进入"可服务"状态；
    昂贵的一次性初始化改成**首次需要时惰性执行**
  - "时好时坏"这个描述本身就是线索：**稳定的网络问题不会时好时坏**，
    交替出现的失败通常指向**协议/状态机缺陷**，而不是环境

### C4｜爆炸后只重建 2 层，漏第 3 层（用户发现）
- **现象**：苦力怕炸穿南墙 y65/66/67，我重建了 y65/y66，**漏了 y67 一格**

### C6｜门口台阶把门堵住（用户发现）

- **规避规则**：放台阶/门槛前先确认两侧地面高度；**齐平就不放**

### C7｜门口照明被炸掉 → 变成固定刷怪点 → 反复被炸（恶性循环）
- **现象**：同一处墙/地面**反复**出现缺口
- **根因**：门口两盏火把被同一次爆炸摧毁 → 门口全黑 → 苦力怕夜间必来 → 再炸
- **规避规则**
  - 房屋**四向 + 门口**必须**全部有照明**（这次补齐 6 盏后才止损）
  - 每次修复后**顺手检查照明**，不要只补砖
  - 发现"同一处反复损坏"时，**先找刷怪原因**，不要只做局部修补

### C8｜搭塔脚手架残留（用户发现"泥土没清除"）
- **现象**：房子西南角立着一根 3 格高泥土柱，还顶掉了一盏火把
- **根因**：机器人用"垫脚搭塔"爬升时留下的方块（`scaffoldingBlocks` 含泥土）
- **规避规则**
  - 任务结束后**清理自己造的临时方块**（塔柱、垫脚）

  - 注意：**天然地形也会有裸土**，要先判断"顶上有草/下方连续"再决定动不动手

### C9｜室内残留施工方块
- **现象**：室内地上/半空留着误放或跳过产生的圆石
- **规避规则**：施工结束**扫描室内体积**，把"非设计方块"清零

### C10｜室内地板原为草地

## E. 连接与模组环境

### E1｜Forge 服务器拒绝原版协议客户端
- **现象**：`Kicked during login: "This server has mods that require Forge to be installed on the client."`
- **根因**：mineflayer 是**原版协议**实现，没有 Forge；而该整合包有模组声明了"客户端必需"
- **规避规则**
  - **Forge/NeoForge**：有客户端模组 → 协议层 bot **不可用**（无解，不是参数问题）
  - **Fabric/Quilt**：不强制模组校验 → 协议层 bot **可以连**（但看不懂模组内容）
  - 想在 Forge 整合包里要"另一个玩家"，走 **方案 A（服务端假玩家）** 或 **方案 B（真实客户端）**
  - 见 `plan-c-1.20.1.md` 与 README

### E2｜首次连接报错不明确
- **现象**：第一次 `ECONNRESET`，第二次才拿到明确的踢出原因
- **规避规则**：连接失败**重试一次**再下结论，第二次的错误信息通常可读

### E3｜装模组**没核对依赖版本区间** → 启动即崩（真实事故）
- **现象**：把 Advanced Peripherals 0.7.46r 装进 ATM9，启动崩溃：
  ```
  Mod advancedperipherals requires computercraft 1.116.1 or above
  Currently, computercraft is 1.115.1
  ```
- **根因**：只确认了"依赖模组**存在**"（CC:Tweaked 已装），**没确认"版本区间满足"**。
  AP 在 0.7.45r 把最低 CC 要求提到了 1.116.1，而 ATM9 自带 1.115.1。
- **规避规则（装模组三步走）**
  1. **版本/加载器匹配**：MC 版本 + forge/neoforge/fabric 必须对上
  2. **读目标 jar 的依赖区间**：`META-INF/mods.toml` 里每条 `[[dependencies.x]]`
     的 `versionRange` 与 `mandatory`
  3. **对照整合包已装版本**判定满足性；**只对 `mandatory=true` 计为"会崩"**
  - 工具：`py tools/inspect_jar.py --jar <jar> --mods <mods目录>`
- **降级优先于升级**：依赖不满足时，**换我自己装的模组**比**动整合包自带模组**安全
  （动自带模组可能连带影响其它 mod 的依赖）

### E4｜**不能用 jar 文件名推断模组版本**
- **现象**：按文件名猜版本，连续误判——
  - `curios-forge-5.14.1+1.20.1.jar` → 被猜成 `1.20.1`（实际 5.14.1）
  - `Botania-1.20.1-448-FORGE.jar` → 被猜成 `1.20.1`（实际 448-FORGE）
- **根因**：文件名里同时存在 **MC 版本**和**模组版本**，格式还不统一；
  部分 jar 的 `version` 字段是构建期占位符 `${file.jarVersion}`
- **规避规则**：**版本号只能读 jar 内 `mods.toml` 的 `version=`**；
  读不到就**如实说"无法可靠判定"**，绝不给一个猜出来的结论

### E5｜工具链在受限环境下的替代方案
- **现象**：`curl.exe` 被沙箱**禁止执行**；`Invoke-WebRequest` 中途断流；
  `api.modrinth.com` 从沙箱内**连不上**
- **规避规则**
  - 下载文件用 **Python（`urllib`）**：`py tools/fetch_mod.py <URL> <路径> <SHA1>`
  - 查 API/网页用**抓取工具**（能访问外网），拿到 JSON 后再交给本地脚本处理
  - 注意：**CDN 可直连，API 不一定**——下载和查询要走不同通道

### E6｜整合包启动**永久卡死**：模组在渲染主线程做阻塞式联网（真实事故）
- **现象**：启动后日志**停止推进**，进程 `Responding=False`，CPU 时间几乎不涨、内存纹丝不动；
  用户观感是"游戏老是不响应/进不去"。**表现为"卡死"，本质是"主线程在等一个连不上的 TCP"**
- **现场堆栈**（`saves` 同级 `logs/latest.log`，同一秒内两条关键记录）：
  ```
  [Render thread/INFO] java.net.ConnectException: Connection timed out: connect
      at java.net.URL.openStream(URL.java:1325)
      at com.hrznstudio.emojiful.CommonClass.readStringFromURL(CommonClass.java:31)
      at com.hrznstudio.emojiful.ClientEmojiHandler.loadCustomEmojis(ClientEmojiHandler.java:70)
      at com.hrznstudio.emojiful.ClientEmojiHandler.preInitEmojis(ClientEmojiHandler.java:62)
      at com.hrznstudio.emojiful.ClientEmojiHandler.setup(ClientEmojiHandler.java:30)
      at net.minecraft.client.Minecraft.handler$zkd000$emojiful_initEmojis(Minecraft.java:6922)
      at net.minecraft.client.Minecraft.<init>(Minecraft.java:589)      ← ★ 构造函数里
  [Render thread/ERROR] An exception was caught whilst loading custom emojis
  java.lang.NullPointerException: ... because "categories" is null
  ```
- **根因链**
  1. Emojiful 用 mixin 注入 **`Minecraft.<init>`（渲染主线程）**，在里面**同步下载**远程 emoji 资源
     （`raw.githubusercontent.com/InnovativeOnlineIndustries/emojiful-assets/master/Categories.yml`）
  2. 目标主机在本机网络下 **TCP 连接超时**（DNS 能解析，连接被卡死）
  3. 下载失败 → `categories` 仍为 `null` → NPE；**`Minecraft` 构造函数从未执行完**
     → 日志永远到不了 `Sound engine started`，游戏永久无响应
- **关键判据**：同一批"要联网"的模组里，**只有跑在主线程上的那个能卡死游戏**。
  本次 Titanium 在 `Thread-43`、Supplementaries 在 `Thread-45`，都只是后台 `WARN` 一下照常继续。
- **本机网络实测对照表**（排查时先测这张表）

  | 主机 | 结果 | 说明 |
  |---|---|---|
  | `github.com` | ✅ HTTP 200 | 通 |
  | `raw.githubusercontent.com` | ❌ **连接超时** | ★ 本次元凶；DNS 正常、TCP 被卡 |
  | `cdn.modrinth.com` | ✅ 可连接 | 下载通道可用 |
  | `api.modrinth.com` | ✅ 可连接（403 为接口层拒绝） | 查询不一定可用 |
  | 系统代理 | ❌ 未启用（`ProxyEnable=0`，无 `HTTP_PROXY`） | 所以直连就是全部 |

- **本次处置**：`Emojiful-Forge-1.20.1-4.2.0.jar` → `Emojiful-Forge-1.20.1-4.2.0.jar.disabled`
  （纯聊天装饰模组，**改后缀即可一行还原**）
- **规避规则**
  - **先分清"卡死"和"加载慢"**：相隔 1 分钟采样两次 **CPU 时间**；不涨 = 卡死。
    ATM9 这类大包正常冷启动要 160+ 秒，但 **CPU 一定在涨**
  - **定位卡死**：在日志里找**最后一条有价值的堆栈**，看它属于**哪个线程**；
    `Render thread` + `Socket.connect`/`URL.openStream` = 主线程被联网卡住
  - **整合包必须能离线启动**：模组在启动阶段联网就是设计缺陷。怀疑时**直接给它断网**（禁用/改配置）验证，比反复重启赌运气快得多
  - 本包内已知启动期联网的模组（全都**只是装饰/统计用途，离线缺失不影响游戏**）：
    Emojiful、Supplementaries（`credits.json`）、Titanium、Ars Nouveau、Immersive Engineering
  - 若确实要它们联网：必须配**全局/TUN 模式的代理或加速器**——
    **游戏加速器通常只代理游戏自身流量，不代理模组的 HTTP 请求**，这是最常见的误判

### E7｜游戏窗口"打不开"：正常位置被写到了屏幕外 + 截屏看不见画面（真实事故）
- **现象**：用户反馈"进入世界后无响应""打不开，根本点不出页面"。
  但进程 `响应=True`、CPU 持续增长、日志正常——**根本不是卡死**
- **真因（两个独立问题叠在一起，各错一次）**
  1. **窗口的"正常位置"本身就是屏幕外**：
     `GetWindowPlacement` 报 `showCmd=1(正常)`，但
     `rcNormalPosition = (-32000,-32000) - (-31840,-31961)`，当前 `rect=(-32000,-32000) size=160x39`。
     `(-32000,-32000)` 是 Windows 存放"最小化 / 被移出屏幕"窗口的**哨兵坐标**。
     因为 `showCmd` 是"正常"，任务栏点击只会把它"还原"回那个屏幕外的点 → **用户永远看不到、也点不出来**
     - 修复：`SetWindowPlacement` 把 `rcNormalPosition` 改成屏幕内坐标，再 `ShowWindow(SW_SHOWNORMAL)` + `SetWindowPos`
     - **反直觉点**：`SetForegroundWindow=True`、`IsHungAppWindow=False`、`IsWindowVisible=True`
       **全都不代表窗口可见**。唯一可信的是 **`GetWindowRect` 的实际坐标**是否落在屏幕范围内
  2. **全屏 GDI 截屏抓不到游戏画面**：
     `CopyFromScreen` / BitBlt 对采用**独立翻转（independent flip）/ 硬件叠加层**渲染的游戏窗口，
     只能抓到桌面背景（游戏那层抓不到）。于是"截屏里没有游戏"被我误读成"游戏没显示"，
     连着三次得出错误结论。本机还查到 `NVOpenGLPbuffer`（NVIDIA Optimus 离屏缓冲）窗口，属同类情况
     - 正确做法：**`PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)`** —— 让窗口自己渲染一帧，能拿到真实画面
- **附带发现**：一个 java 进程有**多个顶层窗口**（真正的 `GLFW30` 游戏窗口、隐藏的 `GLFW message window`、
  `NVOpenGLPbuffer` 等）。要找真窗口：`EnumWindows` 后按 **类名 `GLFW30` + 面积最大**筛，别只看 `MainWindowHandle`
- **规避规则**
  - 判断"窗口在不在屏幕上"**只看 `GetWindowRect` 坐标**，不要相信各种 API 的 `True`
  - 判断"游戏画面正不正常"**用 `PrintWindow`**，绝不要用全屏截屏下结论
  - 排障时先跑 **`& .\tools\grab_window.ps1`**（本次为此新增：自动定位游戏窗口、抓真实画面，
    带 `-Fix` 可一键把屏幕外的窗口搬回来、`-ListOnly` 列出全部窗口）
  - 结论必须落到**坐标与像素**这类硬证据上（`(-32000,-32000)`、`avgBrightness=0`），
    而不是"看起来应该是……"

### E8｜中文回传变乱码：CC 的 JSON 序列化会「逐字节转义」
- **现象**：`say text=hello 我是外部 Agent` 在游戏里正常，但网关收到的上报回来是
  `hello ææ¯å¤é¨`；方块名、玩家名、聊天记录同样会中招
- **排查方法（本次最值钱的一步）**：先分清是**写入方向**还是**上报方向**坏掉——
  **去看 `bridge/processed/` 里我写的那个原文件**。本次该文件里是正确中文
  （`我` = U+6211、无 BOM），于是立刻证明：写入没问题，**问题在回传方向**。
  若不查这一步，极可能误判成"网关读文件没指定编码"而去白改一轮
  （顺带确认：网关 `FileBridge.watch()` 本来就写了 `encoding="utf-8"`，并不是它的问题）
- **根因**：CC:Tweaked 的 `textutils.serializeJSON` 会把字符串里 **0x7F–0xFF 的每一个字节**
  转义成 `\u00XX`（见其 `rom/apis/textutils.lua` 的 `hexify`）。
  于是游戏里正确的 UTF-8 中文「我是」(字节 `E6 88 91`) 在 JSON 里成了
  `\u00E6\u0088\u0091`，Python 解出来就是 3 个 Latin-1 字符 `æ\x88\x91` → **双重编码**
- **处置**：网关新增 `repair_cc_text()`，在 `POST /api/state` 收到上报时按
  「能按 latin-1 编回字节、且这些字节能按 UTF-8 解出」就还原；
  纯 ASCII / 正常 Unicode / 真实 Latin-1 文本一律原样返回。
  自测：`py tools/test_repair.py`（6 个用例，含"正常中文不能被动"的反向保护）
- **规避规则**
  - **跨语言传文本，先确认两端各自的字符串语义**（字节串 vs Unicode），
    不要假设"UTF-8 到处都一样"——Lua 字符串是字节串，Java/Python 是 Unicode
  - 任何"文本过一圈变了样"的问题，**先在中间点落地取证**（本次是 inbox 原文件），
    再决定改哪一端；没有中间证据就改代码 = 赌博
  - 修编码问题时**必须带反向用例**（正常中文、Latin-1 文本不能被改坏），
    否则很可能修好一个、弄坏另一个

- [ ] **两次采样 CPU 时间**（间隔 60 秒）+ `Responding`：
      `Get-Process java | Select Id,Responding,CPU`
      不涨 = **卡死**（不是"整合包大所以慢"）
- [ ] 在日志里找**最后一条堆栈**，读出三件事：**哪个线程 / 哪个模组 / 卡在哪一步**
- [ ] 堆栈里出现 `Socket.connect` / `URL.openStream` / `HttpClient` → 走**联网卡死**流程：
      按上面 E6 的**网络实测对照表**逐主机测连通性
- [ ] 处置优先级：**①禁用该模组（最快、可一行还原） → ②配全局代理/加速器 → ③改 hosts**
      （③ 只在"DNS 解析错"时有效；本次 DNS 正常，纯 TCP 被卡，改 hosts 无用）
- [ ] 处置后**先恢复到主菜单**验证能跑通，再进世界
- [ ] 全程**不要反复重启**——没有新证据的重启只是浪费时间

> **⚠️ 判定纪律（真实误判）**：**单次线程转储不足以判定"卡死"**。
> 本次只采一次堆栈，看到渲染线程正处在 `VoxelShape` 射线检测里，就误判为"卡在碰撞箱"；
> 连续采样三次才发现它在 `BufferUploader` ↔ `limitDisplayFPS` 之间**正常循环渲染**（只是游戏被暂停了）。
> **正确做法**：间隔 10~15 秒连采 3 次，比较**是否停在完全相同的行**；
> 停在同一行 = 卡死或超长单次调用；位置在推进 = **它只是在工作**。
> 同理，单人游戏**窗口失焦会自动暂停**（日志特征：`Saving and pausing game...`），
> 别把"暂停"当成"卡死"。

## G. 五条元规则（最重要）

1. **不要相信工具的"完成"回报**：`placed/skipped/failed` 只是工具的自述。
   凡是结构性成果，一律用**独立扫描计数**验收。
2. **改动前先问"谁靠它撑着"**：门、台阶、火把、红石都依赖支撑块；
   改动前先列依赖，改后立即复查。
3. **重复出现的故障，一定是系统性原因**：
   同一处反复缺方块 → 是**照明/刷怪**问题，不是运气；
   同一接口反复失败 → 是**状态漂移**问题（背包被外部改动/手持物被切换），不是参数问题。
4. **主线程上的阻塞式网络访问 = 无上限卡死**：
   "启动不动了 / 窗口无响应"这类故障，**先问主线程最后在等什么**（网络 / 锁 / 磁盘），
   再去看"是不是包太大、电脑太慢"。**把卡死归因为慢，是最容易浪费一小时的误判**。
5. **凡是写出去的文件，必须回读验证**：
   工具说"已写入"不等于"写对了"——**编码（BOM）、换行、截断**都可能悄悄出错，
   而配置文件写错会以"崩溃"的形式在很久之后才暴露。写配置后**回读首字节 + 首行**，成本几秒。
