# 寻路：参考 mineflayer 与车万女仆，以及我们自己的实现

> 现状：**规划器已经能用 ✓ 执行器还没跑通 ✗**（如实记在 §5 ✓）

## 1. mineflayer（pathfinder）里值得照搬的三件事

| mineflayer 的做法 | 为什么值得学 | 我们的对应物 |
|---|---|---|
| **Movements 代价模型**：平地走 / 上台阶 / 下落 / 跨沟(parkour) / 挖穿(digCost) / 搭桥(placeCost) 各自计价 ✓ | 让"绕远"和"挖穿"能**比价** ✓ 而不是硬性规则 ✗ | `A.path_plan` 里的 dy/cost 分支 ✓ |
| **Goal 抽象**：GoalBlock / GoalNear / GoalXZ / GoalFollow ✓ | 目标不是只有"精确一格" ✓ 大多数时候要的是"到附近" ✓ | 到达判据写成"水平 ≤1 且 y 差 ≤1" ✓（GoalNear 语义 ✓） |
| **thinkTimeout + 重规划** | 一次规划不可能算尽世界 ✓ 走歪了就重来 ✓ | `timeout` / `max_nodes` ✓ + `path_follow` 的 `replans` ✓ |

`mineflayer` 本身是**客户端**：它用 `setControlState`（按键）+ `look` 驱动 ✓ 服务端信它 ✓。
我们的假人**没有客户端** ✗ —— 但 Carpet 把"按键"暴露成了指令 ✓
（`move forward` / `jump` / `sneak` / `look at` ✓）⇒ **架构一一对应** ✓
差别只在：它发数据包 ✓ 我们发指令 ✓。

## 2. 车万女仆（Touhou Little Maid）里最值得学的一件事

女仆的寻路是原版 `GroundPathNavigation`（A* ✓ 与 mineflayer 同源思路 ✓）——
**真正该学的是它的"分层退化"** ✓：

* 走得通 → 走 ✓
* 走不通/卡住/离主人太远 → **直接传送回主人身边** ✓（而不是原地发呆 ✗）

⇒ 我们的策略同构 ✓：**走 → 挖/搭 → 都不行才"回传"** ✓
且**必须如实报告"这次是回传的、不是走过去的"** ✗（不能把兜底伪装成能力 ✓）
`path_follow` 的 `warp` 参数 + 返回里的 `warped` 字段就是为这条服务的 ✓。

另外女仆的**任务系统**（idle/follow/farm/attack + Home 点）✓ 对应我们已有的
job 脚本 + waypoint/GPS ✓ —— 说明方向是对的 ✓。

## 3. 我方实现（已上车 ✓）

* **`A.path_plan`**（只读 ✓ 不发任何移动指令 ✓）：批量读一片区域进内存 ✓
  （`getBlockInfos` 按 4³ ✓ 顺序 y→z→x ✓ 已由 `probe_order` 穷举确认 ✓）⇒ A* 全在内存里跑 ✓
  节点 = "能站的格子" ✓；边 = 走平/上台阶/跳两格/下落/挖穿/搭桥 ✓；八向含斜向 ✓
  （斜向要求两条正交边都可穿 ✓ 与 mineflayer 同规矩 ✓）
* **`A.path_follow`**：逐格走 ✓ 每 3 秒无进展就算卡住 ✓ ⇒ 重规划 ✓ ⇒ 最后才允许回传 ✓
* 防坠崖 ✓（天空岛铁律 ✓ 掉一格就停手 ✓）、总时长上限 ✓、如实汇报 ✓

实测（只读规划 ✓）：
```
path_plan 从麦田 (4110,14) 到熔炉平台 (4143,12)
→ found true ✓ cost 35.92 ✓ steps 34 ✓ visited 189 ✓ scanned 8970 格（约 9.6 秒 ✓）
```

## 4. 本轮挖出的三个"看起来像能力不足、其实是自己写错"的坑 ✗

1. **时间上限把"扫描地图"也算进去了** ✗ ⇒ 扫描 62 秒后搜索一启动就超时 ✓
   现象 `visited: 0` ✓ **看起来像"没路"，其实是"根本没搜"** ✗
   ⇒ 计时改到扫描之后 ✓ + 扫描量上限（默认 24000 格 ✓ 超了直接拒绝 ✓）
2. **可走判据用了 `standable()` 白名单** ✗ ⇒ 309 个模组的方块（土径 ✓ 耕地 ✓ 模组地板 ✓）
   全不在名单里 ⇒ 周围被判成"站不住" ⇒ A* 只扩了 **37** 个节点就枯死 ✓
   ⇒ 改成 **"默认实心 + 例外表"** ✓（只有明确的非实体方块才可穿 ✓）⇒ 立刻找到路 ✓
3. **CC 的 Cobalt 是 Lua 5.1 语义** ✗：我顺手写了 `goto`（5.2+ ✓）⇒ 上机即语法错 ✓
   ⇒ 改用"空区间天然跳过" ✓（`for i = 1, 0 do` 不执行 ✓）

## 5. 执行器 `path_follow`：**已跑通 ✓**（2026-09-20 ✓ 真根因与旧记录**完全不同** ✗）

### 5.1 结果（世界真值 + 磁盘日志双证据 ✓）

| 用例 | 结果 |
|---|---|
| 单步控制 `step_to` (4109,71,16) | `moved: true` ✓（位置真的变了 ✓）|
| **短程** `path_follow` → (4120,71,11) | `reached: true` ✓ 4.2 s ✓ `waypoints: 2` ✓ `warped: false` ✓ |
| **多段** `path_follow` → (4128,71,13) | `reached: true` ✓ **6 个途经点** ✓ 7.0 s ✓ `cost: 7.23` ✓ `replans: 0` ✓ |

`job.log` 侧同步留下完整链路 ✓：
`path_follow.plan_begin → path_plan.scan_done → path_plan.search_done → path_follow.plan_done
 → path_follow.walk_begin → path_follow.walk_done` ✓✓

### 5.2 真根因（**不是**"move forward 的持续性"✗ **不是**"嵌套调用"✗）

```lua
local plan = A.path_plan({ ... })   -- ✗ A.path_plan 返回**两个**值 (true, {…})
                                    --   `local x = f()` 只接第一个 ⇒ plan = true
local okP, res = plan               -- ⇒ okP = true, res = **nil**
⇒ 必然 return false, "规划失败：nil"  -- 一次都没走成 ✗
```

**铁证**（两条独立时间线 ✓）：`act.py` 侧 **4.2 秒**返回 `"规划失败：nil"` ✓
而机器 `job.log` 同一秒里 `path_plan.search_done {found:true, visited:6}` ✓
⇒ **规划器是好的 ✓ 是执行器把结果扔了 ✗**

修法：一行 —— `local okP, res = A.path_plan({ … })` ✓（详见 `docs/错题本.md` **P4** ✓）

### 5.3 顺带纠正旧记录里的两条 ✗

1. **"调用后 90 秒不返回"** ✗ —— 那个 90 秒是 **`tools/act.py` 第 99 行
   `ch.wait(cid, timeout=90.0)`** ✓ 即**客户端**的超时 ✓
   它只能说明"客户端没等到回传"✗ **不能**说明"机器卡了 90 秒"✗（错题本 **P5** ✓）
2. **"硬看门狗没触发"** ✗ —— 原看门狗只在 attempt 循环**开头**判一次 ✓
   而现在**规划本身也有预算**了 ✓（`scan_timeout` ✓）⇒ 单次调用不会再无限期占住执行器 ✓

### 5.4 本轮真正改进的两处设计（都留下 ✓）

* **扫描有预算** ✓（错题本 **P9** ✓）：实测 6851 格 = **8.05 s** ✓ 而搜索 = **0 s** ✓
  ⇒ `timeout` 只管搜索 = **"预算的谎"** ✗ ⇒ 新增 `scan_timeout`（`pathScan` 带 `deadline` ✓）
* **到达判据用"真实坐标"复判** ✓（错题本 **P10** ✓）：
  原来 `reached` **只由"路径计数器走完了"推出来** ✗ ⇒ 会有"报到了、其实没到"✗
  现在按 **GoalNear（取整格差 ≤1）** 复核**真实坐标** ✓ ——
  ⚠ 注意：判据必须与规划器**一致** ✗ 我第一版修得比 GoalNear 更严 ✓ 结果"明明到了却一直重规划"✗

### 5.5 还没做的（据实登记 ✗）

* `walk_to` 仍是"反应式直线走"✗；**复杂地形/绕障**建议直接用 `path_follow` ✓
* `step_to` 的收尾精度约 **0.45~1.3 格** ✓（取决于 CC 的指令往返频率 ✓）
  —— 对 GoalNear 语义够用 ✓ 若要"贴到某一格正中心"✗ 得再做一次微调动作 ✗
* `path_plan` 的**扫描成本**随 radius 立方增长 ✗（约 **67 ms / 4³ 块** ✓）
  ⇒ 远距离请**分段走**（走一段 → 重规划一段 ✓）而不是一步加大 radius ✗
