# 评估：那份架构报告,哪些必要、哪些是过度设计

> 日期：2026-11-02 ｜ 针对：外部提交的 P0/P1 架构整改方案
> 结论先说：**诊断八成是对的，处方偏重了 5~10 倍。**
> 真正必需的 P0 是「**约 1.5 个工作日 + 1 个夜晚机时**」，不是「1.5~2 周」。
> 下面先列核实结果，再逐条判断必要性。

---

## 一、核实：报告里哪些断言是真的

我把每一条都拿去对着仓库量了一遍。

| 报告的断言 | 实测 | 判定 |
|---|---|---|
| 模组主类是 6870 行单类 | `DshBridgeMod.java` **6870 行**，183 个方法 | **真** |
| 265 个 static 可变字段 | 我的正则只数到 **22 个 static 声明（18 个非 final）**；宽松口径也到不了 265 | **存疑，明显夸大** |
| HTTP 单线程，慢请求会堵住 /health | `httpLoop` 是 **单 socket 串行 accept**；无 `ExecutorService`、无线程池 | **真，且是真实风险** |
| `/raw` 以权限 4 跑任意命令 | `httpRunRaw` 用 `CommandSourceStack(..., 4, ...)` | **真** |
| 唯一的边界是绑 127.0.0.1 | 无 token、无 Origin/Referer 校验、无 Host 校验 | **真（CSRF 可行）** |
| 无 req_id / 无错误码闭集 / 无 trace | 响应就是纯文本；Python 用 `ok_of()` 按字符串猜成败 | **真** |
| 任务只存内存，重启即丢 | 模组侧无 journal；jobs 只落 `jobs/*.json` 文件 | **真** |
| 事件环只有 400 条 | `EVENT_KEEP = 400` | **真** |
| 五份真源各自漂移 | `agent/action_schema.json`（50 KB）、`agent/skills.py`（110 KB）、`tools/mc_mcp.py`、`tools/mcp_surface.py`、契约文档表 **都存在且各自维护** | **真（五份并存成立）** |
| 具体数字 55 / 75 / 43 / 41 | 我的快速统计口径不同（mc_mcp 里用另一种写法数到 63 个键），未逐一复现 | **数字待复核，但"不等"这个结论成立** |
| 118 项闸门全绿 | `check_all.py --offline`：`pass=117 fail=0 inconclusive=1 total=118` | **真** |
| D7 一道门都没有 | `doc_consistency_test.py` / `release_check.py` / `scorecard` **都不存在**；唯一提到入口文档的是 `debt_count.py` | **真** |
| `交接提示词.md` 被清空成 17 行 | 实测 **16 行**，内容只剩一段「欠账总账」自动生成块，真正的交接内容（现场/下一步/环境事实/纪律/命令速查）**全没了** | **真，而且比报告说的更糟** |
| reflex 现在 dry_run | `agent/brain.py:268` `Reflex(w, ch, sk=sk, dry_run=True)`，注释写着"只观察（避免抢指令）" | **真** |
| 0 个服务在跑 | 关键服务进程 **0 个** | **真** |
| 0 个计划任务 | 匹配 mc/dsh/agent 的计划任务 **3 个**（可能是无关任务） | 部分真实 |
| 455 MB .git + 2114 行脏区 | `.git` **455 MB**；`git status` 脏文件 **2114** | **真** |
| 73 个历史 jar | mods 目录里 dshbridge 相关文件 **40 个** | 数量待复核 |

**小结**：结构性诊断（单线程、无鉴权、无协议、五份真源、无 D7、入口文档已烂、零服务、脏区巨大）**全部成立**。
两个数字存疑（static 字段数、jar 数），一个待复核（工具数）。

## 二、总判断

报告的**世界观**是对的：这个项目的"能力"长得比"工程骨架"快得多，
现在卡住的不是"能不能做"，而是"**敢不敢让它自己跑一夜**"。

但它的**处方份量**错了一个量级。原因有三个：

1. 它把「单机、单人、本地、测试世界」的处境，当成「多用户、分布式、生产系统」来开药。
2. 它没有看到 **成本模型已经翻转 300 倍** 这件事的真正含义（见第四节）。
3. 它把"未来的可能性"（多智能体全角色、/v2 双栈、god file 拆分）和"现在的阻塞"混在一个 P0 里。

## 三、逐条判断：必要性分级

### 必要，而且便宜（合计约 4~6 小时）

| 项 | 为什么必要 | 成本 |
|---|---|---|
| **HTTP 加固**：accept 用线程池、世界写单独一条车道、加 Origin/Referer 校验、加一个随机 token（写进 `state/`，Python 侧自动读） | CSRF 是真的：本机任何网页都能对 127.0.0.1:8766 发 `text/plain` 的简单请求，不需要预检，直接驱动假人。同时单线程会让一个慢 `/cmd` 把 `/health` 一起堵死 | 2~3 h（一次模组构建+重启） |
| **协议内加信封**（不是 /v2）：回执前面加 `ok=`/`err=<码>`，带 `req_id`、`elapsed_ms`；事件带 `trace` | 现在 Python 用 `ok_of()` 按字符串猜成败，这是最脆弱的一环；加上信封后 118 条判据**一个都不用改**（它们认的还是文本） | 1~2 h |
| **`doc_consistency_test.py`**（D7 第一道门） | 入口文档已经烂到只剩 16 行，而 118 项闸门照样全绿——这证明**没有任何判据在读文档**。先修再立刻加门，否则修完还会烂 | 1 h |
| **重启验收 2.55.1**（手部动画 + 工具切换） | 已经装包但没验；这是唯一一件"5 分钟就能关掉"的未结项 | 10 min |

### 必要，但先要一个前置条件（机时为主）

| 项 | 前置条件 | 成本 |
|---|---|---|
| **D3 混合 soak + scorecard** | **先把测试世界和真实世界分开**（`docs/方案-测试世界与真实世界分离.md` 已经有方案，但没落地）。报告自己在红线里也写了"长测不要在你正在玩的世界上跑" | 2~3 h 搭环境 + 3 夜 × 3 h 机时 |

D3 是唯一一条"如果不过，别的都白搭"的判据（身体不出事）。报告把它列为 P0 是对的。

### 可以缓，收益/成本不划算

| 项 | 我的判断 |
|---|---|
| **`/v2` typed RPC 全套**（12 错误码、版本协商、分页、幂等键、deadline、job_id） | **过度设计**。这是给分布式系统准备的协议，我们只有**一个客户端、一个服务端、一台机器**。真正有价值的是 req_id / deadline / 错误码三样，全部可以在**现有文本协议里增量加**（上面第二行）。另起一套 /v2 意味着两份维护、两套判据、双跑对账一周——为了拿到已经能拿到的东西 |
| **`tool_registry` 生成全部五面** | 方向对，做法太重。这五个面**本来就不是同一种东西**（Lua 动作 75 个是低层原语，MCP 工具是面向 agent 的封装，skills 是更高层组合）。强行用一个生成器统一，等于逼它们变成同一种形状。**正确修法：一张声明式映射表 + 一条漂移判据**，允许"75 个动作里 43 个有工具封装，其余 32 个是原语"这种合法的多对一关系，但不允许**没声明的**漂移 |
| **god file 六阶段拆分（8~10 人日）** | **现在不做**。文件能工作，拆它要动 `mod_contract` 的逐字节锚和 118 条判据，风险远大于收益。等它真的挡住某次具体修改时再拆 |
| **皮肤三路合并（删 BotSkin 245 行）** | 低价值。皮肤不影响任何判据 |
| **多智能体三角色 MVP** | 报告自己的红线说"不要先上全角色"——但它仍把三角色放进 P1 的 19~25 天里。**先做 D3**：身体不稳的时候，多角色只会把不确定性放大三倍 |
| **ForgeConfigSpec / BotContext / tick_lag 采样** | 都是好设计，但都是"为多假人/长时间运行"准备的。**等 D3 过了、真要开第二个假人时再做** |
| **git filter-repo** | 报告自己说可选，我同意。先做 `git rm --cached` + 归档，历史重写可以永远不做 |

### 报告漏掉的、我认为更重要的一件事

**成本模型已经翻转了 300 倍。**

整个系统的设计前提是那句话：**"调用次数是本系统最稀缺的资源"**（一次往返约 0.6 秒）。
53 件工具的分层、"一条指令一份态势"的批处理、蓝图大炮的预计算、CC 计算机这条通道——
**全是为了省调用次数**。

现在直连是 **2~4 ms**，这个前提死了两个数量级。

这意味着：
- 大量"为了省往返"而存在的复杂度，现在是**净负担**，可以删；
- 很多当初"做不了"的判据（例如转身速度剖面的 20 Hz 采样），现在**直接能做**；
- 正确的方向不是"再加一层协议"，而是**回头清算哪些复杂度已经没有存在理由**。

报告在给一个 2~4 ms 的系统设计"分布式协议"，方向正好相反。

## 四、如果我来排：三天的序列（而不是 1.5~2 周）

| 时段 | 做什么 | 产出 |
|---|---|---|
| **第 1 天上午（3 h）** | 重启验 2.55.1；HTTP 加固（线程池 + 世界车道 + Origin + token）；协议信封（`ok=`/`err=`/`req_id`/`elapsed_ms`） | 一次模组构建 + 重启；安全与可观测性同时到位 |
| **第 1 天下午（3 h）** | `doc_consistency_test.py` 并进闸门；恢复 `交接提示词.md`；把 2114 个脏文件分类（该提交的提交、该 ignore 的 ignore、该删的删） | D7 第一道门；仓库回到干净 |
| **第 1 天晚上** | 搭测试世界（禁区 + 固定测试区 + 每轮清理），跑第一档 soak | D3 第一份 scorecard |
| **第 2 天（4 h）** | 真源映射表 + 漂移判据（不生成，只对账）；`release_check`（版本/jar sha256/HEAD/docs 数） | 五份真源从"各自漂移"变成"一份映射 + 一条判据" |
| **第 2~3 天晚上**（机时） | 混合档 soak 连续两夜（idle 20 / walk 30 / work 50），≥2000 次调用，每轮 drain 事件 ring | D3 收口证据 |
| **第 3 天（2 h）** | D1~D7 记分卡把上面全部汇总 | 一张能对外说的验收单 |

合计 **约 12 小时人工 + 3 个夜晚机时**。
剩下的（/v2、god file、多智能体、皮肤、config 化）等 D3 有数据之后再说。

## 五、红线：我同意的，以及要补的

**同意报告的红线**：不要先上多角色；不要一次性切 JSON（118 条判据锚在文本上，改成"文本塞进字段"而不是替换）；不要把世界写并行化；重构 commit 不夹带行为改动；不先重写 git 历史。

**要补三条**：
1. **不要在未验收的模组版本上叠任何新功能**。当前 2.55.1 已装未验，这是唯一一件"十分钟能关掉"的悬空项。
2. **不要在真实存档上做 soak**，而且这条要写进判据（用测试世界的固定坐标 + 禁区 + 每轮清理做前置断言），不能只写在文档里。
3. **每一次"加一层"之前，先问"这一层是不是在为已经不存在的约束买单"**——600 ms 时代的批处理、省调用、预计算，在 2~4 ms 时代应该被重新审视一遍。
