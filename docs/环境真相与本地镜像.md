> 结论一句话 ✓：**网络完全正常** ✓（用户确认 ✓ 实测支持 ✓），

**纪律** ✓：遇到"能握手不能传"✗，先怀疑**应用层/UA 层的拒绝** ✗，不要急着怪网络 ✗。

## 4. ★2026-09-20 更正★：§4 的旧经验有两条是**错的** ✗

> 原文（旧 ✗）：①"按路径选上游" ✓ ②"每次尝试的超时**压到 15~20 秒**" ✗ ③"只对可能有的上游重试" ✓
> 下面逐条对账 ✓ 全部有实测数字 ✓

### 4.1 ✗ "压到 15~20 秒"是**反的** —— 大包根本传不完

| 文件 | 大小 | 实测耗时 |
|---|---|---|
| `slf4j-api-1.7.30.jar` | 41 KB | 1.9 s ✓ |
| `guava-31.1-jre.jar` | 2.96 MB | 14.8 s ✓ |
| **`fastutil-8.3.1.jar`** | **19.0 MB** | **21.1 s** ✗（**超过 20 秒** ✗）|

⇒ 20 秒上限下这个包**永远差一点**✗ ⇒ 镜像报"3 次失败"✗
⇒ Gradle 那边只留下一句 `Skipped due to earlier error` ✗ 再连坐 30 条 ✗（错题本 **P1/P3** ✓）
**已改为 `TIMEOUT = 45`** ✓（`tools/maven_mirror.py` ✓）

### 4.2 ✗ 光"加镜像源"不够 —— **仓库顺序**才是根因（错题本 P2 ✓）

Gradle 在**给出元数据的那个仓库**里认定模块 ✓ 之后**只去那一家取 jar** ✗ 不会去别家补 ✗
⇒ 旧的 `pluginManagement` 把 **bmclapi 放第一** ✗（它有 marker 的 pom ✓ 却**没有 ForgeGradle 的 jar** ✗）
⇒ 无论后面加多少源 ✗ 都救不回来 ✗
**已改为 `/forge` 放最前** ✓（它是唯一一个"元数据与 jar **都有**"的源 ✓ 缓存里 134 个文件为证 ✓）

### 4.3 ✗ 404 不该重试（改在镜像里 ✓ 顺带把日志救回来了）

旧代码对**任何**异常都重试 3 次 ✓ 包括 **404** ✗
⇒ 一个"本来就不存在"的文件（插件 marker 的 `.jar` ✓ `packaging=pom` 的壳没有 jar ✓）
   要白走 **4 个上游 × 3 次 + 每次 sleep** ✗ ≈ 十几秒 / 文件 ✗ ⇒ 日志被刷爆 ✗ 真问题反而看不见 ✗
**已改为：HTTP 404/403 视为"这里确定没有"** ✓ 立刻换下一家 ✓ **只有网络类错误才重试** ✓

## 4.5 ★还有一条更重要的：`plugins { id … version … }` 这条路本身是死的★

- `plugins { id 'net.minecraftforge.gradle' version '6.0.24' }` ⇒ 走 **plugin marker** ✓
  而 marker 的 pom 是 `<packaging>pom</packaging>` ✓ **本来就没有 jar** ✗
  ⇒ Gradle 会去要那个不存在的 `.jar` ✗ ⇒ **一条 404 伪装成 30 条依赖缺失** ✗✗
- **已改成经典写法** ✓（`buildscript { classpath 'net.minecraftforge.gradle:ForgeGradle:6.0.24' }` + `apply plugin:` ✓）
  ⇒ 按普通模块解析 ✓ 没有 marker ✗ 没有那层壳 ✗（详见 `mod/build.gradle` 顶部长注释 ✓）
