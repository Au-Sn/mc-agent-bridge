# 评估（四）：解绑该现在做还是等完善

> 日期：2026-11-02 ｜ 问题：「本模组加 MCP 尚未完善,这个优先级上是否需要考量」
> 一句话答案：**要考量,但考量的是「哪一层」,不是「做不做」。**
> 游戏侧解绑现在做（零损失、成本每天在涨）；大脑侧解绑现在不做,只留接缝。

---

## 一、先纠正一个前提：绑定不是一层,是三层

我扫了一遍"本机程序"到底绑了什么,它们成熟度完全不同：

| 层 | 绑定了什么 | 成熟度 | 解绑性质 |
|---|---|---|---|
| **游戏侧** | 实例路径（24 处）、整合包名（27 处）、存档名（4 处）、假人名（Python 1 + 模组 5）、家坐标、端口（16 处） | **完善**：118 项判据全绿、直连 2~4 ms、世界资产全部验过 | **结构性**：只改配置读取方式,不碰任何行为 |
| **数据侧** | 本包的 20.5 MB 知识（配方 12.4 MB / 注册表 3.5 MB / 标签 3.2 MB / 例外 1.4 MB）＋ 12 处写死注册表数、2 处写死配方数 | 生成器已齐（`kb_export` / `tag_census` / `recipe_index` / `divergence` 都在） | **结构性**：把"引用结果"改成"调用生成" |
| **构建侧** | JDK 302 MB + Gradle 132 MB + 两个 zip 297 MB（合计 731 MB） | 只需要预编译 jar | **纯清理**：发 jar 不发工具链 |
| **大脑侧** | `tools/acp_serve.py` 里写死 `C:\Users\Administrator\...`；启动 `node … dsh --profile mcacp`；依赖外部 `dsh-acp` 服务与一个仓库外的剖面 | **不完善**：依赖外部 harness、剖面在仓库外、ACP 整条链路没有判据守 | **语义性**：冻结它会限制"脑可插拔"的方向 |

**关键事实**：这三层是**解耦的**。我查了关键运行链路——
`mcp_core` / `direct` / `respawn_bot` / `install_mod` / `check_all` / `perceive` / `primitives`
**全部不依赖大脑层**（0/7）。依赖 ACP 的只有 **13 个工具（占 3.6%）**，全是对话/语音/任务相关。

所以"模组加 MCP 尚未完善"这句话，**描述的其实是大脑层**，而大脑层恰好是我建议"不要现在打包"的那一层。

---

## 二、为什么游戏侧解绑不该等

三条理由,一条比一条硬：

1. **它已经完善了。** 拿"完善"当门槛的话,这层早就过线了：118 项判据、直连 2~4 ms、
   虚空平台 256/256、熔炼线 16/16、Create 样机 34/34。等下去的理由不在这层。
2. **成本随工具数线性增长。** 今天 24 个文件各自写死路径；我这两天又新增了十几个工具,
   每加一个都在复制这套写死。**现在做是 1 天,下个月做是 2 天,再往后就是"不敢动"。**
3. **它顺带解决 D3 的前置条件。** D3 需要"测试世界",而"世界可配置"正是解绑要做的第一件事
   （现在存档名写死 4 处）。不做解绑,D3 就只能在你正在玩的世界上泡——那违反我们自己的红线。

---

## 三、为什么大脑侧解绑现在不该做

1. **它不完善,而且"完善"的定义还没定。** 现在连"大脑该接什么协议"都还在试（ACP 是公开协议,
   但剖面、模型、推理档位都还是本机实验态）。**在接口还在动的时候冻结接口,是典型的错误顺序。**
2. **它的绑定是"语义性"的。** 路径写死是结构问题,改完不影响任何设计；
   但"大脑通过什么协议接进来"是**设计决定**——一旦定成某个 harness 的私有形状,就锁死了"可换脑"这条卖点。
3. **它只占 3.6%。** 分发的第一版完全可以**不带大脑层**：发游戏侧（344 个工具）＋ 一个
   **brain 接口声明**（"任何支持 ACP 的客户端都能接"）＋ 一个 stub。这样用户拿到的是
   "一副能用的身体",而不是"半成品的脑"。这比现在硬塞一个半死的 ACP 链路更好用。

## 四、所以优先级怎么排（修正版）

| 优先级 | 做什么 | 为什么 |
|---|---|---|
| **P0（1 天）** | `dsh.env` ＋ `tools/paths.py`：把 24 处路径、整合包名、存档名、bot 名、端口收口到一个文件 | 结构性、零损失、成本每天在涨 |
| **P0（0.5 天）** | 数据"生成而非引用"：`bootstrap.py export` 一条命令按配置重新生成那 20.5 MB；判据改成**读生成结果**而不是写死 24779 / 20764 | 生成器已有,只缺入口；这条一改,换包不再有 14 条红 |
| **P0（0.5 天）** | 新判据 `portability_test`：除 `paths.py` 外,任何 `tools/*.py` 出现 `D:\`、`C:\Users`、整合包名 ⇒ 红 | **这条门是"再也不长回来"的保证**,没有它,解绑会被下一次新增工具冲掉 |
| **P0（0.5 天）** | 模组侧最小改动：3 处裸 `"Bot"` 改回 `WATCHED`；`HTTP_PORT` 与 bot 名进 `ForgeConfigSpec` | 这两项是分发必需,且**不改变任何功能语义** |
| **P0（0.5 天）** | `doctor.py`：把"为什么跑不起来"变成一句人话 | 分发第一版的用户支持成本全在这一步 |
| **P1（等游戏侧解绑完）** | 清脏树、把 731 MB 构建资产移出版本库、删 515 MB 陈旧缓存 | 有了分发需求,这一步终于有正当理由 |
| **P2（等"完善"）** | 公共 API 冻结、MCP 工具面版本化、`/v2` 类型化协议、大脑层打包、god file 拆分 | **语义性**决定,现在冻结会锁死方向 |

**判据式门槛**：什么时候算"足够完善可以冻结接口"？
**工具面 churn 连续两周为 0 ＋ D3 通过。** 在那之前,只做结构性解绑。

## 五、一个容易混淆的点,值得单独说

**"配置化"不等于"接口冻结"。**

这两件事经常被一起推迟,但它们的方向相反：
- 配置化是**把环境事实从代码里搬出去**——它让代码**更可移植**,不限制任何新功能；
- 接口冻结是**把 API 形状钉死**——它让代码**更不可变**,会限制新功能。

所以正确的顺序是：**先配置化（现在）,后冻结（等完善）**。
把两者绑在一起"等完善再做",结果是配置化被无限推迟,而它恰恰是越早做越便宜的那一件。

## 六、给"生成而非引用"的一个具体落法

用户说的"生成而非引用",目前是"半真"的：
- **生成器已经有了**：`kb_export.py`（注册表）、`tag_census.py`（标签）、`recipe_index.py`（配方）、`divergence.py`（分歧清单）——都在。
- **缺的三件事**：① 它们各自写死路径,不读配置；② 没有一条命令按顺序跑完；③ **判据把生成结果写死成数字**（24779 / 20764），而不是读生成出来的文件。

所以这件事的落地形态是：

```
bootstrap.py export
  ├─ 读 dsh.env → 找到 MC_HOME
  ├─ kb_export.py    → state/export_snapshots/*.json
  ├─ tag_census.py   → state/tags_category.json
  ├─ recipe_index.py → build/recipes.json
  └─ doctor 自查：四份文件齐了没有、方块数对不对

判据侧改一行：
  ✗  assert n == 24779            （写死本包数字）
  ✓  assert n == snap["block_count"]   （读生成结果自洽）
```

**这样"换整合包"就不再是 14 条判据变红,而是"重新生成一次,判据自己对齐"。**

## 七、结论

| 问题 | 回答 |
|---|---|
| 解绑该现在做吗？ | **游戏侧、数据侧、构建侧：现在就做。大脑侧：不做,只留接缝。** |
| "尚未完善"影响优先级吗？ | **影响的是范围,不是时机。**不完善的是大脑层（3.6%）,它正好是"不该现在打包"的那层 |
| 会不会白做？ | 不会。配置化不锁定任何设计决定；反而**不做**会让新工具继续复制写死,成本线性上涨 |
| 什么时候再谈冻结？ | 工具面 churn 连续两周为 0 ＋ D3 通过 |
