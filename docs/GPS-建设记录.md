## 二、四条真根因（每一条都让整套系统静默失效 ✗）

### 根因 1：`setblock` 放的调制解调器**只连它朝向的那一侧** ✗
- **现象**：主机全部开着 ✓ startup 也写了 ✓ 但 `gps_probe` 数到 **0 台** ✗；海龟报"需要至少 4 台 GPS 主机" ✗
- **诊断**：`computercraft dump <实例>` ✓ —— **正常的机器会多出一行 `Peripheral top | modem`** ✓
  而故障机器**完全没有 `Peripheral` 那一行** ✗✓
- **根因**：`setblock` 放置的调制解调器默认 `facing=north` ✗；而它位于计算机的**东/西**侧 ✓
  → **CC 的调制解调器只连接到它【朝向】的那一侧** ✓ → 等于**没插** ✗
- **修法**：按相对位置给朝向 ✓（在计算机西侧 → `facing=east` ✓；东侧 → `facing=west` ✓）
  ```mcfunction
  setblock <x> <y> <z> computercraft:wireless_modem_normal[facing=east]
  ```
  改完必须**重启那台计算机** ✓ 再用 `dump` 看 `Peripheral` 行是否出现 ✓✓
- **验证**：H1 修完立刻从"无外设"→`Peripheral right | modem` ✓ 应答数 0→1 ✓ **因果闭合** ✓

### 根因 2：`/computercraft` 命令用的是**实例号**，不是 `ComputerId` ✗
- **现象**：`shutdown 7` / `turn-on 7` 执行了 ✓ 但那台主机**毫无变化** ✗
- **根因**：`data get block` 里的 `ComputerId: 7` ✗ 与 `/computercraft` 认的编号**不是同一套** ✓
  （`dump 7` 返回的是 `Id 0`、位于 `(4136,79,28)` 的**另一台**计算机 ✗✓）
- **修法**：先 `dump` 一批实例号 ✓ 用输出里的 **`Position`** 找到目标 ✓ 再用**那个实例号**发命令 ✓
  （本例：`(4131,71,16)` 的实例号是 **6** ✓ 而它的 ComputerId 是 7 ✓）
- **教训**：**动任何"按编号操作"的命令之前，先确认这个编号是哪一套** ✓

### 根因 3：新放的计算机**开机前没有 `ComputerId`**，而且三条自动开机路径全是假的 ✗
- **实测证伪**：
  | 路径 | 结果 |
  |---|---|
  | `computercraft turn-on <坐标>` | ✗ 无效（无 id 可用 ✓ 错误信息还是中文被渲染成 `?` ✗）|
  | `setblock … computercraft:computer_advanced[state=on]` | ✗ `On: 0b` 不变 |
  | 旁边放红石块 | ✗ 不点亮 |
  | **右键（玩家或假人）** | ✓ **唯一可行** |
- **开机后**：`data get block` 才会出现 `ComputerId: N, On: 1b` ✓
- **写出 startup 后还要重启一次** ✓（`shutdown <实例>` → `turn-on <实例>`）否则它一直停在 shell ✗ 从不执行 `gps host` ✗

### 根因 4：`computer/<id>/` 目录可能**根本不存在** ✗
- **现象**：`[System.IO.File]::WriteAllText(...)` → `DirectoryNotFoundException` ✗
- **修法**：先 `New-Item -ItemType Directory -Force "$dir\<id>"` ✓ 再写 ✓（id 4 就没有目录 ✓）

## 六、海龟导航：两个新踩的坑（2026-09-17 续）

### 坑 1（我自己写的脚本造成的）：直接调 `turtle.turnRight()` 会让朝向"表里不一" ✗
- **现象**：`goto (4119,71,17)` 报"连续 3 步没有靠近目标 ✓ 停在 `4121,71,1` ✓ 当前朝向 south" ✗
  —— 目标在南边 ✓ 它却**往北走了 3 步** ✗（方向正好反 180° ✓）
- **根因**：我在 `probe_neighbors.lua` 结尾写了"回到原来的朝向" ✗ 但用的是
  **3 次 turnRight + 1 次 turnLeft** ✗ = 净转 **180°** ✗（正确应是 3 次 turnLeft ✓）；
  而且我**直接调用 `turtle.turnRight()`** ✗ 绕过了 worker 的 `ACT.turn_right` ✓
  → worker 内部的 `facingIdx` **完全不知道转过了** ✗ → 之后所有轴向移动全反 ✓
- **修法**：
  1. 脚本里要转回原位就**用 worker 的动作** ✓（`ACT.turn_left` / `ACT.turn_right` ✓）不要裸调 `turtle.turnX` ✗
  2. 一旦怀疑朝向错了 ✓ **读方块状态**（`block_state <x> <y> <z>` → `state.facing` ✓ 那是**权威** ✓）
     再用 `calibrate facing=<真实朝向>` 校准 ✓ —— **不要相信 status 里的 facing** ✗（那是内部索引 ✓ 可能已经错了 ✓）
- **验证**：校准后 `goto` 立刻恢复"往正确方向走" ✓（从 z=1 走到 z=8 ✓ 朝南 ✓）

### 坑 2：海龟的无线调制解调器是**升级**，不是旁边的方块 ✓
- **现象**：`peripheral.getType("left")` 说 left 是 `modem` ✗ 而 `turtle.inspect()` 说左边那格是
  `advancedperipherals:inventory_manager` ✓ —— 同一侧两种说法 ✓ 我一度怀疑"外设注册表过期" ✗
- **真相**（方块实体 NBT 一次看懂 ✓）：`LeftUpgrade: "computercraft:wireless_modem_normal"` ✓✓
  —— **调制解调器是装在升级槽里的** ✓ 所以它作为一个"外设"出现在 left ✓
  而**旁边那格**的 inventory_manager 是另一回事 ✓ 两者并不矛盾 ✓
- **教训**：遇到"同一个东西两种说法" ✗ 不要先假设是缓存/时序问题 ✗
  → **直接把方块实体的 NBT 打出来** ✓（`data get block` / `block_state` 里的 `block_entity` 字段 ✓）
  一次就能看清全部真相 ✓（这次它同时给出了 Owner / Fuel / Items / ComputerId / LeftUpgrade ✓）

## 八、作业脚本的边界：`ACT` 是局部的，脚本里拿不到 ⚠

- **现象**：`run_job` 返回 **`attempt to index global 'ACT' (a nil value)`** ✗
- **根因**：turtle worker 里的 `ACT` 是一个 **局部表** ✓
  而 `run_job` 执行作业用的是 `load(src, name, "t", _ENV)` ✓
  → 脚本拿到的是**全局环境** ✓ **看不到 worker 的局部表** ✗
- **证据**：只用标准 API 的三个脚本**全部正常** ✓
  （`fetch_barrel.lua` ✓ `peek_containers.lua` ✓ `probe_refresh.lua` ✓）
  而用到 `ACT.*` 的两个**全部报这个错** ✗（`probe_neighbors.lua` 改过的那版 ✗、`clean_stray.lua` ✗）
- **规则**：
  1. **作业脚本只能使用 CC 标准 API** ✓：`turtle.*` / `peripheral.*` / `gps.*` / `fs.*` / `os.*` / `sleep` ✓
  2. 要用 worker 的高级动作（`goto` ✓ `place_row` ✓ `chop_log` ✓ `craft` ✓ …）
     就**由 Agent 逐条下发** ✓ 不要写进作业脚本 ✗
  3. 想让脚本也能自主导航 ✓ 就在脚本里用 **`gps.locate()`** ✓ 自己维护朝向 ✓
     （自校准办法：先前进一格 ✓ 再定位一次 ✓ 坐标差就是"前方"的方向 ✓ 然后退回来 ✓）
- **附带好处**：这种错误**在第一行就抛异常** ✓ → 不会造成部分执行 ✗（本次没动过任何方块 ✓ 已用世界状态确认 ✓）

## 十、⚠⚠ 把自己锁在门外：**不要通过机器自己的通道去重启它**

- **我做错的**：想给 cmd0 加载新版 Lua ✓ 于是发了两条服务器指令给它自己：

  → **一台关着的机器永远取不到自己的开机指令** ✗✗ 死锁 ✓
  （判据：网关 `state.json` 里 `queues.cmd0` **卡在 8 不再变化** ✓ 而 cc0 心跳仍新鲜 ✓
    → 说明不是网关坏 ✓ 而是 cmd0 没在取 ✓ 且它最后心跳时间正好是 shutdown 那一刻 ✓）
- **更严重的一面**：cmd0 是**唯一**的命令计算机 ✓ → 它一关 ✓ 我就**再也发不了任何 `/` 指令** ✗
  （`survey` ✓ `block_state` ✓ `setblock` ✓ `/computercraft` 全都走它 ✗）
  → **世界状态的读取通道也随之断了** ✗（只剩海龟自己的 `turtle.inspect` 能看邻格 ✓）
- **正确做法（三条，任一即可）**：
  1. **让玩家/另一个命令计算机**去开机 ✓（`/computercraft turn-on 2` 在聊天栏里打 ✓ 或右键方块 ✓）

  3. **绝不要**把 `shutdown` 和 `turn-on` 一起丢给同一台机器的同一队列 ✗
- **顺带**：CC 里的 **ComputerId 存在物品 NBT 里** ✓ → 把方块挖下来再放回去**会保留 id 与文件系统** ✓✓
  （所以"挖掉→放回→右键开机"是一条理论可行的自救路 ✓ 但风险高 ✗ 不是首选 ✓）

## 十一、自己写导航的两个代价（作业脚本版）

**背景**：作业脚本里拿不到 `ACT` ✗（见 §8 ✓）→ 我在 `clean_stray2.lua` 里自己写了一版
`goTo()`（`gps.locate` + 转向 + 前进 ✓ 带自校准 ✓）。它**逻辑是对的** ✓ 但**性能不可接受** ✗：

| 问题 | 实测证据 | 应该怎么做 |
|---|---|---|
| **每一步都调 `gps.locate(3)`** ✗ | 每步最坏 3 秒 ✓ → 140 步预算 = 最坏 **7 分钟/格** ✗ → 13 格要跑一个多小时 ✗（磁盘日志 4 分钟只写 1 行 ✓） | 用 **worker 的 `goto`** ✓ 它内部同样定位但**有"连续 3 步没靠近就停"** ✓✓ 实测 20 格只用几十秒 ✓ |
| **没有防卡死** ✗ | 我的 `goTo` 只会把预算跑光 ✗ 外面看到的就是"沉默" ✓ | 照抄 worker 的**进度保护** ✓：连续几步没靠近目标就**立刻报错退出并回报现场** ✓ |

**结论（写进原则）**：
1. **能用 worker 的动作就用 worker 的动作** ✓（`goto` ✓ `place_row` ✓ `chop_log` ✓ `craft` ✓）
   作业脚本只负责**做那一下**（挖 ✓ 放 ✓ 收 ✓）✓ ✓ 逐格由 Agent 侧小步下发 ✓
2. **长作业必须每格写磁盘进度** ✓（本轮已经补上 ✓ 于是"在跑 vs 卡死"终于可分辨 ✓✓）
3. **别一次下 13 格** ✗ —— 我这是第二次犯同一个错 ✓（第一次是 13 段导航 ✓ 第二次是 13 格回收 ✓）
   → **3~4 格一批 ✓ 每批世界验收 ✓**






## 五、方法论（今晚最大的收获）

> **"我观测到的"和"世界真实的样子"之间，永远隔着一层我自己写的代码。**

今晚同一个病犯了三次 ✓ 每次的产物都是一个**看起来完全合理、而且我很有信心**的错误结论 ✓：

| 我写的代码 | 我因此得出的错结论 | 真相 |
|---|---|---|
| 读轮转日志但不看时间戳 | "只有 1 台 GPS 主机在应答" | 其实 3 台 ✓ |
| 用相对路径写文件 | "探测请求已下发" | 文件根本没进收件箱 ✓ |
| 主手槽位写死成 5 | "equip 失败了" | 斧头一直在手上 ✓ |

**三条硬规矩**（已写进 `agent/` 的注释里 ✓）：
1. **每个数字都要能追到它的原始出处** ✓（哪个字段、哪条权威来源 ✓）
2. **任何"结果"都要看时间戳** ✓ —— "内容合理"与"内容是现在的"是两件事 ✓
3. **先验证最便宜的前置条件** ✓ 再编排后面 5 步 ✓（前置没验证，后面全是在赌 ✓）
