# 模组方案：让假人能正常存取容器（`dshbridge`）

> 用户拍板 ✓：「还是需要写东西让假人可以正常拿取箱中物品，**可以写成模组**」✓
> 本文是这个模组的**最小可行设计** ✓ 以及"为什么非得写模组" ✓

---

## 1. 为什么 KubeJS / `/item` 都不够（都试过 ✗）

| 路线 | 实测结果 |
|---|---|
| 原版 `/item replace block <pos> container.N …` | **对原版熔炉可用** ✓ 但对**模组容器直接报"不是容器"** ✗（`sophisticatedstorage:netherite_barrel` 实测 ✗）原因：它走的是原版 `Container` 接口 ✗，模组容器只有 Forge 的 **`IItemHandler` 能力** ✓ |
| KubeJS `block.inventory` | 只对原版容器稳 ✓ 模组容器不可靠 ✗，且语义是"脚本替它搬"✗ 不是"它自己拿"✗ |
| 漏斗喂料（世界机制） | **可用 ✓ 且已实测打通** ✓（桶顶放朝下漏斗 + 把东西丢给它 ✓ ⇒ 真的进了桶 ✓）—— 但它只能**存**✓ 不能**取**✗，还要占一个漏斗 ✓ |

⇒ 缺的那一块是：**"以假人身份、按能力接口、跟任何容器打交道"** ✓ —— 这正是模组该做的事 ✓。

## 2. 最小设计（就三个指令 ✓ 别的都不做 ✓）

模组 id：`dshbridge` ✓（Forge 1.20.1-47.2.20 ✓）

```
/dshbox peek <x> <y> <z>                  # 看容器里有什么（只读 ✓ 给智能体"眼睛"✓）
/dshbox take <x> <y> <z> [<物品子串>] [数量]  # 把东西搬进**执行者自己的背包** ✓
/dshbox put  <x> <y> <z> [<物品子串>] [数量]  # 把背包里的东西放进容器 ✓
```

**为什么是指令、不是 CC 外设或 GUI** ✓：
* 现有桥接**本来就是用指令驱动游戏**的 ✓（cmd0 有 2 级权限 ✓）⇒ 加指令 = **零新增管道** ✓
* 指令的**回传文本**天然就是"可被桥接读到"的证据 ✓（与 `data get` 同一套 ✓）
* 不用客户端代码 ✓ 不用 Mixin ✓ ⇒ 这个模组会很小 ✓ 很好维护 ✓

**实现要点（都来自本项目的血泪 ✓）**：
1. 取容器一律走 **`ForgeCapabilities.ITEM_HANDLER`** ✓ ⇒ 原生支持所有模组容器 ✓
2. **先确认放得下，再扣容器里的东西** ✓ —— 这条是本项目最贵的教训之一 ✗
   （KubeJS 版合成核心就因为在背包满时静默吞物品 ✗ 丢过铁锭和矿石 ✗）
   `take` 满背包时应当**明确拒绝**并回一句"背包满" ✓ 而不是搬一半 ✗
3. 每次只回传**结构化摘要** ✓（搬了哪些、各多少、剩余多少 ✓）⇒ 智能体可自证 ✓
4. 一切都在**服务端** ✓ 假人就是普通 `ServerPlayer` ✓ 不需要特判 ✓

### 6.4 为什么 `/dshuse` 是这一版最值钱的一条 ✓

**筛矿就死在它身上** ✗（错题本 **P16** ✓）：
- 站在同层或更低处打筛子的**侧面** ⇒ `use` **每一步都回 `success:true`** ✓
  而筛子 NBT **一个字节都不变** ✗（`progress`/`contents` 原样 ✗）
- 站到**高一格**、让射线上方**射进碗里**（命中面 = `up`）⇒ `progress 0.8 → 0.0` ＋ 出碎块 ✓

⇒ `dshuse` 把"**打哪个面**"变成**显式参数** ✓ ⇒ 这类坑从此可以在**调用点**说清楚 ✓
（`aimy` 就是给碗形方块准备的 ✓ 筛子用 0.15 ✓）
