# 评估（三）：这个项目能不能打包给别人用

> 日期：2026-11-02 ｜ 触发：用户要求「后续该项目需要打包给其他人使用」
> 直接回答：**现在打包出去，换一台机器 100% 跑不起来。**但不是因为代码烂，
> 而是因为它**从来没为"别人"写过一个配置项**——所有环境事实都是写死的。
> 好消息：修起来不难（约 3 天），因为 Python 侧是纯标准库、模组是自包含的。

---

## 一、先说清楚：会怎样失效

我自己扫了一遍（只读），四个层面的耦合是硬的：

| 耦合 | 实测 | 换环境后的后果 |
|---|---|---|
| **实例路径** | 24 个工具各自写死 `D:\pcl2\.minecraft\versions\All the Mods 9 - To the Sky - atm9sky`（每个文件 1 处，共 24 处重复定义） | 换机器/换盘符/换目录名，这 24 个工具**直接崩**（`install_mod.py`、`world_alive.py`、`kb_export.py`、`structures.py` 全在内） |
| **整合包身份** | 27 处硬编码整合包名 | 换整合包 ⇒ 名字对不上，数据生成与校验全错位 |
| **假人名字** | `mcp_core.BOT = "Bot"`；模组里 `WATCHED = "Bot"`，但另有 **3 处**又直接写 `"Bot"`（L2193/L2376 等，绕过了 `WATCHED`） | 别人如果不想叫 Bot，改一处不够，得改五处 |
| **家/屋坐标** | `no_dig.py` 默认禁区写死 `(4115,71,19)-(4129,79,32)` | 别人的家不在那 ⇒ **禁区保护形同虚设**（既不保护他的家，还会禁止他挖一片莫名其妙的区域） |
| **存档名** | 4 处写死「新的世界 / 新的世界 (1)」 | 名字不同 ⇒ 读盘类工具（`cc_logs.py`、`find_item_in_save.py`）失效 |
| **整合包数据数字** | 12 处写死注册表方块数 **24779**、2 处写死配方数 **20764** | 换整合包 ⇒ 这 **14 条判据直接红**（它们是"覆盖率/完整性"判据，把本包的数字当成了世界常数） |
| **端口** | 8765 出现在 8 处、8766 出现在 8 处 | 端口冲突时不能改（模组里是 `static final`） |
| **运行前提** | 模组编译只依赖 Forge（好），但**运行**依赖 Carpet 假人；存档里要有那台假人；直连要求游戏已进世界 | 别人缺 Carpet ⇒ 连假人都没有；没进世界 ⇒ 8766 不监听 |

**结论**：换环境不是"可能失效"，是**必然失效在第一步**（脚本找不到实例目录）。

## 二、但有三件有利的事,别高估难度

1. **Python 侧是纯标准库**。我扫了 357 个工具 ＋ agent ＋ gateway，**没有第三方依赖**
   （唯一的 `python-docx` 出现在我今天刚写的 md→docx 转换器里，不属于运行链路）
   ⇒ 别人**不需要 pip、不需要 venv**，装个 Python 3.10+ 就能跑。这省掉了打包最恶心的部分。
2. **模组是自包含的**。`build.gradle` 只依赖 `net.minecraftforge:forge`，**没有 Carpet 编译依赖**
   ⇒ 可以直接发**预编译好的 jar**，别人不需要 JDK、不需要 Gradle。
   这也正好解释：仓库里那 429 MB 的 JDK/Gradle 工具链**根本不该放进分发包**。
3. **直连让分发变简单了**。以前分发包还得带 CC 计算机的 Lua 程序 ＋ 网关 ＋ 存档里那台计算机；
   现在模组自己开 HTTP 口，**别人只要装 mod + 跑 Python 就行**，CC 那套降级成可选后备。

## 三、耦合分四级：哪些必须改、哪些只是数据

### 第 1 级：硬编码（必须改成配置，否则跑不起来）

| 项 | 现在 | 改成 |
|---|---|---|
| 实例路径 | 24 处各写一遍 | 一个 `dsh.env`（或 `config.json`）＋ 一个 `paths.py` 统一读；支持环境变量覆盖与自动探测 |
| 存档名 | 4 处 | 同上 |
| 假人名 | Python 1 处 + 模组 5 处（其中 3 处绕过了 `WATCHED`） | 配置项；模组侧先用 `WATCHED` 把 3 处收口，再抽成 Forge 配置 |
| 端口 | 16 处 | 配置项（模组侧进 `ForgeConfigSpec`） |
| 家/屋坐标 | `no_dig.py` 默认值 | **首次运行引导**：让用户标一次家（或 `from scan` 自动取当前站位的 bbox），写进 `state/no_dig.json` |

### 第 2 级：本包生成的**数据**（不该分发,该让新机器自己生成）

| 文件 | 体量 | 性质 |
|---|---|---|
| `build/recipes.json` | 12.4 MB | 从本包 311 个 jar 里抽出来的配方 |
| `state/export_snapshots/` | 3.5 MB | 24779 个方块的注册表导出 |
| `state/tags_category.json` | 3.2 MB | 本包的标签分类 |
| `state/exceptions.json` | 1.4 MB | 手工攒的分类例外 |

**这四份合计约 20.5 MB，全是"这个整合包的知识"。** 换整合包就毫无意义。
正确的做法不是"打包带走"，而是**带走生成器**（`kb_export.py`、`tag_census.py`、`recipe_index.py`、`divergence.py` 都在），
让新机器**十分钟内从自己的包重新生成一遍**。

### 第 3 级：需要一起跑一次的引导（首次启动）

- 检查 Forge 版本 / Carpet 是否存在 / 存档是否已加载 / 8766 是否空闲
- 生成上面那 20 MB 数据
- 拉假人（`/raw player Bot spawn at ...`）并把落点写进配置
- 标一次家，写入禁区

### 第 4 级：可以照抄的（不用改）

- `mod/src/`（自包含）
- `tools/` 的判据主体（118 项里绝大多数是逻辑判据，与本包无关）
- `agent/`、`gateway/`、`cc-tweaked/`（可选后备）
- `docs/`（除了带数字的那几份）

## 四、打包设计：一份配置 ＋ 三个脚本

### 1. `dsh.env`（一份配置,取代 24 处硬编码）

```ini
# 必填
MC_HOME=D:\pcl2\.minecraft\versions\All the Mods 9 - To the Sky - atm9sky
MC_WORLD=新的世界 (1)
BOT_NAME=Bot
HTTP_PORT=8766
# 可选
GATEWAY_PORT=8765
HOME_BBOX=auto            # 或 4115,71,19,4129,79,32
PACK_NAME=auto            # 从 MC_HOME 目录名推
```

配套 `tools/paths.py`：读 env → 全部模块 import 它 → **24 处重复定义变成 1 处**。

### 2. `bootstrap.py`（首次引导,幂等）

```
① doctor：检查 Python 版本 / MC 目录 / 存档 / Forge / Carpet / 端口
② export：从本机整合包生成 recipes / registry / tags（10 分钟）
③ spawn：拉假人，记录落点
④ home：让用户标家（或取当前站位 3 格范围），写 no_dig
⑤ verify：跑一遍离线闸门 + 直连自检
```

### 3. `doctor.py`（诊断,随时可跑）

把"为什么跑不起来"变成一句人话：Python 版本不对 / 找不到 MC 目录 / 游戏没进世界 /
8766 没监听 / Carpet 没装 / 假人不在 / 数据未生成。

### 4. `cold_start_test.py`（D8,分发的验收判据）

**这是这个项目缺的最后一道门**：把"项目能跑"和"项目能递给别人跑"分开量。

判据（模拟一次干净机器）：
- 从一份**只含源码 + 文档 + 配置模板**的目录出发（不含 state/build/logs/tmp）；
- 只允许用 `bootstrap.py` 一条命令完成引导；
- 断言：`doctor` 全绿、`check_all --offline` 全绿（与本包无关的那部分）、直连握手成功、假人就位；
- **人工改三项配置**（bot 名 / 端口 / 家坐标）后重跑，仍全绿。

## 五、分发什么、不分发什么

| 分发 | 不分发 |
|---|---|
| `mod/build/libs/dshbridge-2.55.1.jar`（预编译,约 126 KB） | `mod/jdk17.zip`（178 MB）、`mod/gradle-8.1.1-bin.zip`（119 MB）、`mod/gdist`（132 MB）、`mod/jdk`（302 MB）——**共 731 MB 构建期资产** |
| `tools/*.py`（纯标准库）、`agent/`、`gateway/`、`cc-tweaked/`（可选） | `tmp/`（2707 个跟踪文件）、`*.pyc`（957 个）、`logs/`（46 MB 运行痕迹） |
| `docs/`（除带本包数字的几份）、`mod/src/`（想自己改的人用） | `state/` 与本包相关的数据（20 MB）、`map_cache`（34 MB）、`downloads/`（5 MB） |
| `dsh.env.example`、`bootstrap.py`、`doctor.py`、`requirements.txt`（空的,标注"纯标准库"） | `.git`（455 MB）——分发用 **源码包 + jar**,不用仓库 |

**分发包大小估算**：工具＋文档＋源码约 15 MB，jar 0.13 MB，**合计约 15 MB**。
跟现在 1.99 GB 的工作区比，差两个数量级。

## 六、这件事和前面两份审计的关系

有意思的是：**这一份需求，给前两份审计里"该不该做"的争论判了胜负**。

1. 仓库审计说"429 MB 工具链在库里是浪费"——当时我的判断是"本地仓库，磁盘不是瓶颈，收益是数字好看"。
   **现在它有了正当理由**：分发包**绝对不能**带 JDK/Gradle，而这 429 MB 进了 git 就意味着
   `git clone` / 打源码包时会带出去。所以**移出版本库是打包的前置条件**。
2. 架构审计说"/v2 协议、god file 拆分"——**这些和分发无关**，反而会推迟分发。
   分发真正需要的是：配置化、引导、诊断、冷启动判据。
3. 所以优先级要再调一次：**打包（3 天）应当插到 D3 soak 之前**，
   因为 D3 需要"测试世界"，而"世界可配置"正是打包要解决的第一件事。

## 七、实施顺序（约 3 天）

| 天 | 做什么 | 验收 |
|---|---|---|
| 第 1 天 | `dsh.env` + `tools/paths.py`；把 24 处路径、世界名、bot 名、端口全部收口；模组侧把 3 处裸 `"Bot"` 改成 `WATCHED`，端口进 `ForgeConfigSpec` | 在本机用**三套不同配置**各跑一次 doctor + 闸门，全绿 |
| 第 2 天 | `bootstrap.py`（doctor/export/spawn/home/verify）＋ `doctor.py`；把 20 MB 包数据从"随包分发"改成"首次生成" | 删掉 `state/` 与 `build/` 后，一条命令 10 分钟重建 |
| 第 3 天 | `cold_start_test.py`（D8）进闸门；`dsh.env.example`；分发说明（30 行）；打包脚本 `make_dist.ps1`（只打白名单） | 从空目录跑通冷启动；分发包约 15 MB |

**不做**（与本需求无关）：git 历史重写、god file 拆分、/v2 协议、多智能体全角色。

---

## 八、一句提醒

"能打包给别人"这件事的真正门槛，不是路径，**是那份 20 MB 的整合包知识**。
它是这个项目最值钱也最不可迁移的部分。
所以分发设计的核心不是"把我的数据带上"，而是"**让别人的机器按同样的方法生成一遍他自己的数据**"——
带走生成器，不带走结论。这一点如果搞反了，分发包会变成一个只能在我的世界上跑的东西。
