## 1. 蓝图大炮到底是什么（拆成可实现的三件套）

| Create 的部件 | 它做的事 | 我们的对应物 |
|---|---|---|
| **蓝图**（Schematic，一份数据文件） | 记录"哪些相对位置放什么方块" | `cc-tweaked/blueprints/<名>.json` ✓ 网关 `/files/blueprints/…` 下发 ✓ |
| **大炮本体** | 带着蓝图飞过去，**逐块**放置 | 桥接动作 **`A.blueprint_build`** ✓ 让假人 tp 到观察位逐块放 ✓ |
| **缺料清单（checklist）** | 先算账：缺什么、缺多少 | `blueprint.py plan` ✓ 对着现场 diff + 比对背包 ✓ **不够就拒绝开炮** ✓ |
| **跳过已符合的格子** | 幂等、可中断续做 | 每格先读回 ✓ 一致就跳过 ✓ 由 `already/skipped/remaining` 如实报出 ✓ |

**一句话**：不是把方块"变"出来 ✗，而是**用假人自己的材料、按蓝图一块块放** ✓ ——
与"真人拿着蓝图手搭"语义相同 ✓ 只是它能自己飞、自己核对 ✓。

## 2. 读图那一半：结构化快照（世界信息获取的升级）

新动作 **`A.snapshot`**（把零散 `readBlock` 换成批量读 ✓）：

* 底层用 Advanced Peripherals 的 **`commands.getBlockInfos(minX…maxZ)`** ✓ 一次读一整块 ✓
* 两条既有结论直接决定实现 ✓（见 `docs/carpet-route-progress.md`）：
  1. **体积上限**：17³ 直接 `Too many blocks` ✗ ⇒ 按 **4³ 分块** ✓
  2. 返回项**不带坐标** ✗ ⇒ 顺序 = **y（最外）→ z（中）→ x（最内）** ✓
     （当初用"批量 vs 单点逐格"对照 + 穷举 6 种排列定下来的 ✓ **不能靠猜** ✗）
* 回传：`cells`（只含非空气 ✓）+ 逐类 `counts` + `solid_n/air_n/volume` ✓ + 边界盒 ✓

能力上的变化很实在 ✓：
* `capture` 把一片区域**存成蓝图** ✓（相当于"蓝图与笔"✓）
* `plan` 对着现场**算差异与缺料** ✓（相当于炮的 checklist ✓）
* 验收也用它 ✓：搭完读一次快照，**哪些格真的是木板**一目了然 ✓（本轮就是这么验收的 ✓）

## 3. 几何上的一堵硬墙（这门炮最关键的一处结论）

**事实：站在平台顶面时，同高度方块的侧面永远点不到** ✗ —— 这是几何上无解 ✗，不是参数没调好 ✗。

推导（设脚下那块为 ref，顶面 y=Y+1；目标在它旁边、同一层）：
* 眼睛在 `Y+2.62` ✓ 想打中目标侧面（y∈[Y, Y+1]）⇒ 射线在 x=X+1 处必须下降 ≤1.62 ✓
* 但射线在到达 x=X+1 **之前**，必然先穿过平面 `y=Y+1` ✓
* 而那正是**脚下那块方块的顶面** ✓ ⇒ 落点永远是自己脚下那格的顶面 ✓

真人的解法（MC-93117）✓：**潜行把身体探出边缘**，让眼睛越过那个面 ✓。
⇒ 我们的做法：tp 到 ref 顶上、**越过共享面 0.05 格** ✓ 再回看侧面 ✓；
此时约 55% 悬空、但仍与 ref 有重叠 ⇒ 服务端判定"站在地上" ✓ 不会掉 ✗。

**实测印证** ✓：修正站位前 `placed: 0`（失败原因全是"四周没有可贴的完整方块"或打偏 ✗）；
修正后**第一轮就 `placed: 6`** ✓。

## 4. 施工规则（都是踩过或推出来的 ✓）

1. **参照优先级**：左右邻居（点侧面 ✓ 平台外扩就是这种）> 下方（点顶面）> 上方（点底面）✓
2. **顺序**：y 升序 → 离锚点水平距离 ✓ —— 像炮一样**从锚点一圈圈长出去** ✓
   乱序会长出够不着的孤立块 ✗
3. **观察位**：必须**脚下有支撑** ✓（虚空上的格子站不住 ✗ 会直接坠下去 ✗）
   纵向情形要站"旁边有支撑"的格子 ✓（半径 1~2 搜 ✓ 虚空边缘那块"岸上地形"往往就在 2 格外 ✓）
4. **飞**：悬空平台上的观察位本身在尚未长出来的格子上 ✓ ⇒ 只能 tp ✓
   （与"炮沿轨道飞行"同构 ✓ 也让 `max=` **分批**成为可能 ✓）
5. **报数不看指令回显** ✓：每格放完**读回**该格 ✓ 只有真变成目标方块才算 `placed` ✓
