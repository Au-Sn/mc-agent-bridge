## 五、它漏掉的：清完还会再脏

审计给的是**一次性清理单**，没有给**防复发的判据**。这是它最大的短板。

必须加两道闸门，否则这次的 576 MB 三个月后会长回来：

| 新判据 | 守什么 |
|---|---|
| `repo_hygiene_test.py` | 跟踪文件里**单个 > 5 MB 的非源码文件**必须白名单声明；`*.jar` / `*.zip` / `*.pyc` / `*.class` 不许被跟踪；`.git` 体积和跟踪总量设上限，超了就红 |
| `doc_consistency_test.py`（上一份报告叫 D7） | 版本号 / jar 字节数 / HEAD / 工具数 / docs 数 / 台账节数 / 入口文档行数 / 链接可达 —— 任何一项与实测不符就红 |

这两道门加起来不到 200 行，但它们能保证：**这次清完，下次不会烂**。

## 六、我不同意或要修正的

### 1. 不支持做 git 历史重写（P2 的 filter-repo）

审计说这是"收益最大"的一项（455 MB → 25~40 MB）。我不同意，理由是**成本被低估了**：

- 670 个提交 **hash 全变**；
- 实测 **81 处提交 hash 引用、分布在 11 个文件**；
- 更关键的是**台账 668 节和 181 条错题的证据链**大量用 "§79.xxx 见提交 abcdefg" 这种引用——hash 一变，这些引用**全部失效**，而这是这个项目最值钱的资产之一（可追溯的决策史）。

**收益是什么**：本地仓库从 455 MB 降到几十 MB。**这台机器磁盘不是瓶颈，仓库无 remote、不共享。**
所以这是"数字好看"而不是"解决痛点"。

**建议**：接受 455 MB，只做 `git rm --cached`（把工具链移出**索引**，盘上文件保留，离线构建不受影响）。
如果哪天要推送/共享，再做 filter-repo——那时 hash 失效是必须付的代价。
另外 `secrets/deepseek.key` 已轮换（`secrets/deepseek.key.REVOKED`），**本地无共享前不算风险**；真要共享，filter-repo 是必须的。

### 2. `tmp` 退出索引解决不了 `.git` 体积

`git rm --cached tmp` 让工作区变干净，但**历史 blob 仍然在 pack 里**（7.38 MB）——它只解决 dirty tree，不解决体积。这跟审计的表述略有出入，别指望这一步瘦身太多。

### 3. `mod/jdk` 本来就不在库里

审计写"mod/jdk 磁盘，只移出版本库不删"——实测它从来没进过库（`git ls-files mod/jdk` = 0）。所以只需保留，不需要"移出"。

### 4. 三块工具链的处置我同意，但顺序要改

审计把 `mod/gdist` / `mod/jdk17.zip` / `gradle zip` 放在"需人工确认（B 档）"。
我的判断：**盘上不能删**（本机能连不上 services.gradle.org，这是离线构建资产），但**可以从索引移出**（`git rm --cached`），因为盘上文件还在，构建照常。这一步没有风险，不必"确认"。

### 5. `docs/` 一次性审计文档不要"移到 history"就完事

审计建议把审计/裁决类文档移 `docs/history/`。
我同意**别裸删**，但要注意：`birth_gate_test.py` 会拿 `docs/*.md` 全文当登记语料。移动目录会改变 glob 结果，**必须先跑一次闸门确认**。审计自己也提了这条红线，很好——但它把"移动"当成低风险动作，实际是"移动 + 闸门"两步。
