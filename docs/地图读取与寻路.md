## 1. 为什么不能"逐格读"（先量再设计 ✓）

实测（`tools/m1_measure.py` ✓ 2026-09-23 ✓）：

| 量的事 | 结果 | 含义 |
|---|---|---|
| 一次 1x1 方块读取 | 中位 **0.617 s** | 一格 0.6 秒 ✗ 29x29 要 **8 分钟** ✗ |
| 一次 41x21x41 大盒子扫描 | **1.42 s**（模组内部只花 `us=560` ✓） | 贵的是**桥的往返** ✗ 不是扫描 ✓ |
| `dshscan box "kind" 1000 1` | `matched=248 shown=248` **一次给全** ✓ | ★按种类批量取坐标★ ✓ |
| 翻页 `page=2/3` | 坐标确实不同 ✓ | 收不完可以翻 ✓ |
| `#tag` 查询（`#minecraft:mineable/shovel`） | `matched=1023 shown=1000` ✓ | 一次上千个坐标 ✓ |

⇒ **建图的路子** ✓：先拿这一片的**种类清单** ✓（不带 `match` 的那次回执头部就带 `counts[...]` ✓）
  ⇒ 每种**一次**调用（`max=1000` ✓）拿回它**所有坐标** ✓
  ⇒ 每个 `(x,z)` 柱子里**最高**的那个方块 = 地表 ✓

**代价对比** ✓：同样一大片 ⇒ 逐格 **504 秒** ✗ vs 按种类 **约 36 秒** ✓ ⇒ 快一个数量级以上 ✓

## 2. 两个"实测撞出来"的坑（都写进代码了 ✓）

### 2.1 子串匹配 ⇒ 标注会串（`grass` vs `grass_block` ✓）

`dshscan ... "grass"` 是**子串**匹配 ✓ ⇒ 它把 `grass_block` 的坐标也一起给回来 ✓
若先按 `grass` 记 ⇒ 那格被标成 `minecraft:grass`（草 ✓ 植物）而真身是 `grass_block` ✗
（验收脚本当场抓出 **3/14 不一致** ✓）

**修法** ✓：按**名字长度降序**处理 ✓ 已被认领的格子不覆盖 ✓
（`grass_block` ⊆ `grass` ✓ 先认长的正好对 ✓；格子键是 `(x,y,z)` ✓ 一格只属于一个方块 ✓）

### 2.2 "最高那个"不等于"你脚下那层"（树冠 ✗）

直接取最高 ⇒ 树冠 `oak_leaves@74` 被当地表 ✗ ⇒ 会规划到**树顶**上去 ✗
**修法** ✓：`surface(x, z, below=层+1)` ✓ —— 问"这一层**下面**最高的实心是什么" ✓

## 3. 寻路：为什么要另起一条

老路 `walk_to` 只有一条指令 ✓ 近距离够用 ✓（实测 4~6 秒 ✓）但：

| 症状（实测 ✓） | 真因 |
|---|---|
| 常报 `unreachable` ✗ | 目标格**本身站不住**（小数坐标取整 ⇒ 落到半砖/庄稼/箱子那格 ✗） |
| 中途被挡就整条失败 ✗ | 没有全局图 ✓ 只在局部看 ✓ |
| 走 5 格却 `step_downs=19` ✓ | 绕路 ✓ 因为它不知道整体地形 ✓ |
| ★**掉进虚空**★ ✗ | 目标挑在平台边上 ✓ 一脚踩空 ✓（2026-09-23 真发生 ✓ 见 §5 ✓） |

**新路** ✓（`pathplan.Planner` ＋ `walk_route`）：

```
建图（mapread ✓）⇒ A* 全局规划（4/8 邻 ✓ 不切角 ✓ 落差 +1/-3 ✓）
   ⇒ 化简（只留拐点 ✓）⇒ 拆腿（每条 ≤6 格 ✓）
   ⇒ 一条一条走 ⇒ ★每腿用 dshdigest 验一次真实位置★
   ⇒ 走偏/被挡 ⇒ 从**实测位置**重规划（最多 2 次 ✓ 每次打出来 ✓）
```

**三道安全闸** ✓（★事故之后加的★ ✓）：
1. **连通区域** ✓：目标和起点必须在**同一块连通的平台**上 ✓
   （隔着虚空的"孤岛"哪怕有地板 ⇒ **坚决不去** ✗ 并说清"中间是虚空" ✓）
2. **内陆格** ✓：目标若在平台边上 ⇒ 自动挪到最近的**四邻都能站**的格子 ✓ 并明说挪了 ✓
3. **腿短** ✓：每条腿 ≤6 格 ⇒ 模组那个局部寻路没多少地方可以乱走 ✓

## 7. R3：把"逐段走"提速（A/B 实测 ✓ 一路踩坑 ✓）

**起因** ✓：R2 里"逐段走"稳但慢 ✗（同一段路：老 `walk_to` 4~6 秒 ✓ 逐段 14~53 秒 ✗）

| 轮次 | 改了什么 | 实测（同一批 12 格路段） |
|---|---|---|
| ① | 只把轮询从 0.4 秒改成"先睡再查" | 反而更慢 ✗ **413 秒** —— 真因不在轮询 ✓ |
| ② | 长跳（≤12 格一跳）＋ 没成才退化成逐段 | 3/3 到位 ✓ 但 **243 秒** ✗ |
| ③ | 图框**钉在 8 格网格**上（原来假人一动框就变 ⇒ 每次重建图 ✗） | 第一段 211 秒 → **8 秒** ✓ |
| ④ | **地板模型修正**（见下 ✓）：航点不再落在庄稼顶上 | 第一段 8 秒 ✓ 3/3 ✓ |
| ⑤ | 图框钉在 **16 格网格** ＋ 半径 28 ＋ 缓存 30 分钟 | 稳态段 **6~11 秒** ✓ |
| ⑥ | 每跳只读一次位置（省一次往返）＋ 估时调紧 | 稳态 **6~11 秒** ✓ vs 老路 4 秒 ⇒ **约 1.5~2.4 倍** |

**结论（诚实版 ✓）**：
- `walk_route` 现在是**一跳走 12 格 ＋ 每跳验一次真实位置 ＋ 失败自动退化** ✓ 3/3 到位 ✓
- 稳态比老 `walk_to` 慢**约 1.5~2.4 倍** ✗ —— 代价买的是：**每一步都有世界真值背书** ✓
  ＋ **拒绝去危险的地方** ✓ ＋ **被挡了会自动重规划** ✓
- 剩下的慢，主因是**模组那个局部寻路的单跳耗时**（有时一跳要 10~25 秒 ✗）
  ⇒ 这一条已经写进 v2.15 的模组改动里 ✓（见 §8 ✓）
- 判据 T2（≤1.5×）**当前是 FAIL** ✗ —— 我把它**留在文档里不删** ✓
  （等 v2.15 生效后重测 ✓ 现在改判据就是自欺 ✓）

### 7.1 ★地板模型：这一轮最大的坑★ ✗

- 第一版把"柱子里**最高**的方块"当**地板** ✗ ⇒ 小麦/草/火把/树叶/栅栏全被当地板 ✗
- 后果 ✗：规划出的航点落在**庄稼顶上** ✓ ⇒ 模组走过去**站不住** ⇒ 一步 0.3 格地挣扎 ✗
  ⇒ 实测：12 格的一段路走了 **37 条腿 / 211 秒** ✗（而且看起来像"模组寻路不行"✗）
- 修法 ✓：`mapread.is_floor()`（黑名单法人话版 ✓）＋ 与模组**同一口径**（模组用**碰撞箱** ✓）
- 教训 ✓：**"能站"必须问"踩得实不实"** ✗ —— 与 P78（"能站"≠"安全"）是**一对** ✓
