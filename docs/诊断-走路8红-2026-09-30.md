## 1. 根因（一句话）

**假人正站在一只 `sophisticatedstorage:netherite_barrel` 的顶盖上（格 `(4122,72,4)`，脚 `y=73.00`），而它四邻平台真实的行走层是 `y=71` —— 一步落差 2 格。**

**模组自己有两套互相矛盾的落差口径**：搜路（A*）允许下落 **2~3 格**（`ASTAR_DY={0,1,-1,-2,-3}`），而每 tick 的执行闸只认**下 1 格**（只看 `nb.below()` / `nb.below(2)`）。于是 A* 规划出来的第一步永远是「降 2 格」，tick 执行器当场否决 ⇒ `result=edge`、**位移 0.00**、`path=0/N`（一个航点都没推进）、**而且不重规划**。

⇒ **安全规则把假人关在桶顶上下不来**。这正是 P124「安全规则**能把人关在里面**」的同一族 —— 只不过这次锁在**模组执行器**这一层，而不是中间层的回程守卫。

## 3. 判据 Q3：`put_many` 是不是同一个根因

**是「走路这一族」，但机制不同 —— 它死在导航的第一步，一行 `dshbox` 都没发。**

1. 源码：`tools/mc_mcp.py:781 _box_many()` ⇒ 先 `_near(x,y,z)`；`_near` 返回 bad 就
   `return "✗ 没走到容器旁边 ⇒ **没动手**"`（`786–788`），**其后所有容器操作（`dshbox`）都不会执行** ✓
2. 电池日志：`put_many: 9.5s err=True | _near calls=1 dshwalk=4 **dshbox=0** channel=8`
   ⇒ **`dshbox=0`** ⇒ 它就是在 `_near` 那一步退出的 ✓（不是「搬不动」、也不是「容器读不出来」）
3. `_near`（`365–379`）先试 `(x+1, y, z)`，再试 `(x, y, z+1)` —— 对容器 `(4122,72,4)` 就是
   **`(4123,72,4)`** 与 **`(4122,72,5)`**，**用的是容器自己的那一层（y=72）**。
4. 世界真值（E2 独立读）：
   - `(4123,71,4) = minecraft:air` ⇒ `(4123,72,4)` **脚下没地板 ⇒ 不是能站的格**
   - `(4122,72,5) = computercraft:wireless_modem_normal` ⇒ 脚层被占 ⇒ **也不是能站的格**
5. 真跑这两条（F 段，只走，不碰容器）：
   ```
   F1  M._walk(4123, 72, 4) ⇒ bad=True
       | 走到 (4123,72,4)：**没到** ✗（reached）｜ 停在 4122.93,73.00,4.29 偏差 0.61 格 ｜ 驱动=auto
       | ★★模组说「到了」、实测**不算到**★★：在目标那一格里 = False ｜ 层对得上 = False
   F2  M._walk(4122, 72, 5) ⇒ bad=True

       | 同上：在目标那一格里 = False ｜ 层对得上 = False
   ```
   ⇒ **两条都 bad ⇒ `_near` 必返回 bad ⇒ `_box_many` 在「不读容器、不发 `dshbox`」的情况下退出** ⇒ 与电池的 `dshbox=0` 形状完全一致 ✓

**两个具体机制叠在一起：**
- (a) **`_near` 的落脚格口径错**：它拿**容器自己的 y** 当「站到旁边」的坐标，而这只桶旁边的真实落脚层比它**低一层** ⇒ 那两个候选格**天生站不住**。这不是「被安全规则拦」，是**目标格本身不存在**。
- (b) **模组的到达判据太松**（`3627`：水平 ≤ `stop` 且 `|dy| ≤ 1.3`）⇒ 把「站在旁边一格、高一层」报成 `reached`（F1/F2 实测）⇒ 工具层只能用**世界真值复核**把它否掉（`mc_mcp.py:180–204` 那段「模组说到了、我也要自己复核」）⇒ 于是又变成「没走到」✗

⇒ **`put_many` 不是「搬不动」，是「根本没走到」。** 与那 8 条同族（**模组的层/落差口径与真实世界不一致**），但**直接成因是中间层 `_near` 的候选格挑错**。

## 5. 顺带挖到的另外两条真 bug（不是本案主因，但会持续制造「层全错」）

### 5.1 模组的到达判据 (`3627`)
`dist <= stop && |dy| <= 1.3`，`dist` **只算水平** ⇒ 「站在旁边一格、高一层」被判 `reached`。
实测（F1/F2）：模组报 `reached`，而世界真值 `在目标那一格里 = False ｜ 层对得上 = False`。
⇒ 这把中间层的判断也带偏了（`_near` 因此判 bad）。

### 5.2 模组的 `standable()` / `floorOk()` 不认「碰撞箱顶有多高」(`3361–3368`)
只判 `!getCollisionShape().isEmpty()` ⇒ **薄板方块会被当成一整格地板**。
实测：`(4122,72,5) = computercraft:wireless_modem_normal`（薄板）；
- `dshmap` 的高度行说那一列能站在 **`y=73`**（`0`）
- 而**实际站上去的世界真值是 `pos=4122.57,72.19,5.63`** ⇒ **模型偏高 0.81 格** ✓
⇒ 建议：`floorOk()` 应当按碰撞箱的 `max(Y)` 定「脚高」，而不是「非空就算一整格」。

### 5.3 `edge` 那个 `why` 用词本身也在误导
`why=edge ahead: no support at 4121, 72, 4` 里的「no support / 没有支撑」**听起来像虚空**，而实际是「下面 2 格有结实的 `chipped:calcite_bricks`」。
⇒ `walk_diag.py` 的 D4 归类会把它归到「说不清」（因为它按「虚空/边走/回不来」这些词匹配，而这里写的是 `no support`）—— 建议这条 `why` 明确写成 **`step_down=2 > max_step_down=1`** 之类。
